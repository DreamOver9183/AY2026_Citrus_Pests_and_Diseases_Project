## 0. 一句話結論

**v11 計畫書要求的 353 張新照片，從頭到尾不是必要條件。**

v11 §3 有一條沒被檢驗的前提——「train 維持現有規模不縮水」。
放掉這條，把既有影像從 train 移進評估集，就能讓**全部九類的
pooled ±2SE ≤ 0.10**（v11 §2 訂的 B 級目標），代價是 raw train 少 6.0%。

另外在建置過程中查到一個**存在於 v5r／v5.5、影響全部九個類別**的增強缺陷
（見 §2.2），v5.6 一併修掉。

## 2. 逐項說明

### 2.1 調整資料集切分 ✅

#### 量測到的擴充上限

用 `check_dataset_leakage.py` 的 dHash 分群跑在 v5.5 的 raw 影像上：

| 類別 | raw 池 | train 中「非近重複單張」 | 現有 eval | **eval 上限** |
| --- | ---: | ---: | ---: | ---: |
| Citrus_Leaf_Miner | 201 | **161（全部）** | 40 | **201** |
| Thrips_Damage | 208 | **166（全部）** | 42 | **208** |
| Scale_Insect | 251 | **201（全部）** | 50 | **251** |
| Thrips | 554 | 306 | 79 | 385 |

**三個問題類別一個近重複群組都沒有**——擴充評估集不會踩到洩漏，
唯一的代價是 train 變小。這是先前沒有量過、因此被誤以為做不到的事。

#### 新切分：逐類絕對評估量，且與 v5.5 巢狀相容

**v5.5 的 valid/test 成員全部保留，新增的評估影像只從 v5.5 的 train 抽。**
於是 `v5.6 eval ⊇ v5.5 eval`，v10 的數字可以在「v5.5 子集」上重算直接對照，
不會因為換切分而失去可比性。實作用 md5 還原 provenance
（`write_sample` 走 `shutil.copy2`，是位元複製）。

| 類別 | 池 | v5.5 v/t | **v5.6 v/t** | raw train | Δ | pooled ±2SE |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Citrus_Leaf_Miner | 201 | 20/20 | **45/45** | 161→111 | −31% | 0.210→**0.099** |
| Thrips_Damage | 208 | 21/21 | **40/40** | 166→128 | −23% | 0.161→**0.082** |
| Thrips | 554 | 40/39 | **60/60** | 475→434 | −8.6% | 0.170→**0.097** |
| Scale_Insect | 251 | 25/25 | **35/35** | 201→181 | −10% | 0.082→**0.049** |
| 其餘五類 + Background | — | 不變 | **完全不動** | 不變 | 0 | 0.016–0.043 |

- **全部九類 pooled ±2SE ≤ 0.10**，最差 0.099
- raw train 2,502→2,353（−6.0%）；eval 653→**802**（+22.8%）

> **pooled 的前提**：必須 `patience=0` + 固定輪數，valid 才沒有參與任何決策、
> 才能合法與 test 併計（[v11 §5](v11_計畫_資料擴充與切分重新設計.md)、
> [v10 §6](v10_結果_v5.5首次訓練評估.md)）。這是訓練協定的改動，資料集本身不受影響。

#### 必須事先聲明的代價

**CLM 的 raw train 少掉 31%**，是全案最集中的風險。
**預先登記判準**：若 CLM 的 AP50 下降幅度超過它自己的 ±2SE（0.099），
就回退到 35/35（train raw 131、±2SE 0.112）。

### 2.2 影像處理 ✅ ——順帶查到一個影響全部九類的缺陷

#### 【主要發現】任意角度旋轉讓所有類別的框系統性變大

Albumentations 旋轉 bbox 的做法是「把原框四個角轉一轉，再取新的外接矩形」。
對**任何**框這都是高估——**正方形框轉 15°，外接矩形面積變成 1.50 倍**。
物件沒有變大，只有標註變鬆了。

v5r／v5.5 的全域管線帶著 `Affine(rotate=(-15,15), p=0.5)`。實測 v5.5 的 train
（增強圖 vs 原始圖的框面積中位數比）：

| 類別 | 面積比 | | 類別 | 面積比 |
| --- | ---: | --- | --- | ---: |
| Sooty_Mold | 1.075 | | Citrus_Leaf_Miner | 1.136 |
| Aphid | 1.100 | | Thrips | 1.184 |
| Scale_Insect | 1.108 | | **Thrips_Damage** | **1.300** |
| Black_Spot | 1.115 | | | |
| Canker | 1.116 | | | |
| Oily_Spot | 1.135 | | | |

理論預期（±15°、p=0.5、平均 |7.5°|）約 1.13x，**實測與預期吻合**。

膨脹幅度由框的長寬比決定，而長寬比最大的 `Thrips_Damage`（p50 2.05、p90 3.68）
膨脹最嚴重——**它同時也是定位最差的類別**（medIoU 0.725、R@0.75 = 0.29）。
這個關係在九個類別上單調成立。

增強圖佔 train 的 45–75%，所以模型有相當比例的監督訊號是「偏大的框」，
這會特別傷 mAP@0.5:0.95 這種高 IoU 門檻的指標——
v10 實測 mAP50 0.809 但 mAP50-95 只有 0.606。

**修正：旋轉一律只用 90° 的整數倍**（`RandomRotate90`）。90° 旋轉把緊貼的
外接矩形映射成另一個緊貼的外接矩形，**零膨脹**，而且提供 4 個朝向、
角度多樣性比 ±15° 更高。田間手持照本來就沒有固定朝向。

`aug_profiles.ROTATE_MODE = "legacy15"` 可切回舊行為供 A/B 對照。

#### 【第二項修正】邊界填充由 REFLECT_101 改為 REPLICATE

`Affine` 平移／縮放後要填補空出的邊界。v5r 用 `BORDER_REFLECT_101`（鏡射），
理由是避開 `BORDER_CONSTANT` 的黑楔——黑楔只出現在增強圖上，會變成假捷徑。
這個理由仍然成立，但鏡射有一個沒被注意到的副作用：**它會把物件複製好幾份**，
而 Albumentations 會（正確地）替每一份補一個框。

第一次建置時實測：`Thrips` 有 **180/493 張**增強圖的框數多於來源，
平均 2.03 倍。抽出來看，是一隻薊馬被鏡射成上下左右四份的萬花筒畫面，
邊緣被接縫切掉的還產生了「半隻蟲」的框。

改用 `BORDER_REPLICATE`（邊緣像素向外延伸）：邊界是一道拉長的糊影，
**不可能複製出第二個物件**，也不會有黑楔。驗收 Gate 5 現在硬性檢查
「沒有任何增強圖的框比它的來源多」。

#### 逐類 profile

| Profile | 相對 `_default` 新增 | 依據 |
| --- | --- | --- |
| `_default`（6 類） | 旋轉改 90° 倍數、邊界改 REPLICATE、加 `VerticalFlip` | 上述兩項修正 |
| `Thrips` | 同 `_default` | 見下方「沒有用縮放補小框」 |
| `Citrus_Leaf_Miner` | `RandomShadow(p=0.2)`、`RandomToneCurve`、`PlanckianJitter`、亮度對比放寬到 ±0.25 | v11 §3.1 明列缺「受光照與背景干擾」；v10 顯示 P > R（漏檢型）。**全部是光度算子，不動框座標，零標註語意風險** |
| `Thrips_Damage` | `RandomToneCurve` | 問題是框不準而非漏檢，所以只補光度多樣性、不加任何動到框的算子 |

**三條寫進程式的硬性約束**（`aug_profiles._assert_ops`）：

1. 旋轉只能是 90° 的整數倍
2. 四個病害類別的色相偏移鎖死 ±3°（SOP §5.1：防止綠葉被推成病斑黃）
3. 不使用 `CoarseDropout`——它會讓 GT 變成 amodal（框住被遮擋的完整目標），
   與人工標註的 modal 約定不一致

**不調高 `AUG_MULT`。** 現行 train 已有 75% 是增強圖，同一批來源再多複製幾份
不增加任何資訊，只會加深 v10 §1 已觀察到的 ep50 後過擬合。

#### 【已知限制】為什麼沒有用縮放去補 Thrips 的小框

`Thrips` 在 `32–96px` 帶的召回只有 0.429/0.529，而 `>256px` 帶是 1.000。
train 帶內佔比 11.5%、評估集 29.7%。**這個落差是真的**——
v5.6 把評估集擴大到 120 張之後仍然存在（v5.5 的 79 張時是 34.9%），
所以不是抽樣雜訊。

成因是**去洩漏規則的必然後果**：連拍的近重複群組一律整群移進 train，
而連拍的田間照傾向拍較大的目標，train 因此被系統性灌滿大框。

試過兩條路，都不可行（實測，quota = 493）：

| 做法 | train 帶內佔比 | 問題 |
| --- | ---: | --- |
| `scale=(0.90,1.10)`（現行） | 10.9% | — |
| `scale=(0.65,1.05)` | 13.9% | 幾乎沒動 |
| `scale=(0.45,1.05)` | 14.4% | 仍然幾乎沒動 |
| 偏向小框來源加權抽樣 | 38–43% | **434 張 train 只有 34 張含帶內的框**，會被各重複 14–19 次 |

縮放無效的原因：Thrips 的框主體落在 200–450px，乘 0.45 還有 90–200px，
多數仍然跨不進這個很窄的帶。加權有效但代價是犧牲場景多樣性。

**結論：用現有影像池無法在不造假的前提下補上這個落差。**
列為 v5.6 的已知限制據實寫明，而不是用會產生假影的增強去湊一個數字。
真正的解法需要改去洩漏規則（會讓評估集含群內近重複、虛增有效樣本數，
是更糟的交換）或新拍照片（本次前提排除）。

### 2.3 影像剪接 copy-paste ❌ ——實作、實測、否決

#### ultralytics 內建的 `copy_paste` 對本專案是 no-op

```python
# ultralytics/data/augment.py  CopyPaste.__call__
if len(labels["instances"].segments) == 0 or self.p == 0:
    return labels
```

本專案是**純方框標註**（`segments` 永遠是空的），所以把 `copy_paste`
超參數調成任何值都不會有任何效果。要做就必須離線自建。

#### 自建了，然後實測不合格

設計：把 CLM 食痕以 `cv2.seamlessClone` 融進 train 的健康株影像
（`Healthy/Murcott` + `Ponkan` 共 400 張，其中 320 張在 train）。
這兩者**完全同域**（都是 2048×1536 田間手持照），理論上能把 CLM 的
背景多樣性從 111 擴到 431。

產了 30 張、送人工驗收之前先自己看過：**只有約 10 張堪用**，
遠低於原訂 28/30 的門檻。兩種失敗：

| 失敗 | 樣態 | 嚴重性 |
| --- | --- | --- |
| **顏色發散** | 貼上區域整塊變成紫／藍紫 | 明顯假影 |
| **框裡是空的** | 融合把貼片洗淡到看不見，只剩框畫在乾淨葉面上 | **更嚴重——等於製造沒有物件的標註** |

#### 根因是標註形態，不是融合方式

換過四種做法對照（`MIXED_CLONE` / `NORMAL_CLONE` / `NORMAL`+色彩對齊 /
直接貼+色彩對齊）都救不了。

**本專案是方框標註，「剪下食痕」實際上剪下的是一個方形區域**，
裡面除了食痕還有葉緣、樹枝、天空。貼到另一片葉子中間就會出現
「葉子中央長出一段葉緣」這種不可能的畫面；而融合程式為了讓邊界自然
會洗淡整塊，洗到最後食痕消失，只剩空框。

要做對需要**食痕本身的輪廓遮罩**，而取得它 = 用輪廓重標一次 CLM——
那個工時拿去標真實照片顯然更划算。

**處置**：`--arm cp` 不啟用；`tools/copy_paste_clm.py` 保留，
檔頭記錄完整失敗分析；原訂的 C 工作包**取消**，不占用組員時間，
30 張與四種做法的對照圖留在
`人工標註/C_合成圖_看圖打勾/證據/` 當紀錄。

> **這不是白做的。** 它確定了「影像剪接」這條路對方框標註的專案不可行，
> 之後不必再有人試一次。而且失敗模式二（空框標註）如果沒有先看就直接進訓練集，
> 會是很難事後追查的汙染。

### 2.4 網路搜尋 ⚠️ ——結論是「此路不通」，這本身就是有用的結果

#### 本地 `craft_datasets_undone`

| 資料集 | 張數 | 相關類別 | 阻礙 |
| --- | ---: | --- | --- |
| Large-Scale Lemon Leaf → `Citrus Leafminer` | 900 | CLM | 無標註；512×512 **白底去背單葉**；125 張逐位元重複；**只有 506 個獨立場景**（56%），含一個 235 張的巨大群組 |
| `CitrusUAT_dataset` | 953 | CLM | 有 Masks/ROIs，但**遮罩是葉片輪廓不是病斑**（前景佔比 21% = 整片葉子），推導出的框會框住整葉；離體葉片放灰墊 |
| Large-Scale Lemon Leaf → `Citrus_Pest` | 542 | CLM（食痕最清楚） | 無標註；離體葉片放白紙 |
| `Citrus Leaf Disease Image` | 607 | 無（都是已達標的病害類） | 無標註、分類用 |
| `train/` | 38,432 | 無 | 無標註、分類用 |

**五個外部資料集全部沒有任何標註檔**——資料夾即標籤的分類集，做偵測要從零標框。

#### 網路搜尋

| 缺口類別 | 找到什麼 | 可用性 |
| --- | --- | --- |
| **Citrus_Leaf_Miner** | 多個孟加拉檸檬葉資料集（CitrusLeafVision 1,238、BDLemonLeaf 含 125 張 leafminer、Citrus Leaf Disease 650） | ❌ 全是離體葉分類集，無框，同樣的域問題 |
| **Thrips** | 公開偵測資料集**全部是黃色黏板**（TPest-RCNN、AgriPest21 24,412 張、各式黏板 YOLO 模型） | ❌ 域完全不符——我們要的是葉片上的薊馬 |
| **Thrips_Damage** | **找不到任何資料集**，只有 UC IPM / EPPO / Koppert 的圖鑑頁面 | ❌ |

#### 決定性的問題是域，不是數量

我們的部署域是 **2048×1536 手持田間照**（果園背景、土壤、雜草、自然陰影、
甚至入鏡的手指）。外部資料集全部是**離體單葉放在白紙／灰墊上**。

**把離體葉照片混進 CLM，等於重蹈 [P3 §1.4](v9_說明_P3定位精度改善與測試流程.md)
記載的覆轍**——Thrips 的蟲體子域混了顯微／圖鑑照，導致框定義不一致、
AP50 好而 AP50-95 差。

因此外部資料**只能進 train、必須當獨立實驗臂**，而且試點規模刻意壓到 150 張：
先用最小的代價回答「有沒有用」，而不是先投入 953 張的標註工時再來後悔。

> **這一節最有價值的部分是排除法。** 它確立了「先找現成資料」這條路走不通，
> 之後不必有人再重複調查一次。

### 2.5 圖片生成 ❌

不採用，三個理由：

1. **省不到人力**。生成的影像沒有可信的 GT 框，仍然要人工標——
   而人工標註正是本專案最稀缺的資源。既然都要標，標真實照片顯然更好。
2. **本機沒有 GPU**（`torch 2.13.0+cpu`）。要在 Kaggle 上跑
   SD + ControlNet + 標註 + 域檢查，是數天的工程量，換到的是不可量化的收益。
3. **細微蟲體形態正是生成模型最不可靠的地方**。2mm 的薊馬、蜿蜒的潛葉蛾食痕，
   都需要生成器準確重現病理特徵——這是它最容易編造的部分，
   而編造出來的病徵會直接汙染訓練訊號。

生成唯一擅長的是**背景多樣性**，但我們已經有 400 張健康株負樣本，
背景從來不是瓶頸。

## 3. v5.6 是什麼

**九類、`train 7,264 / valid 401 / test 401`**，目錄結構完全比照 v5.5：

```
Datasets/Datasets_YOLO26_v5.6/
├── Diseases/  Healthy/  Pests/        ← 自足來源樹，與 v5.5 位元一致
├── 人工標註/{A,B,C}/                   ← 三個工作包
└── OutPut/{train,valid,test}/{images,labels} + data.yaml + _provenance.json
```

順帶修掉一個既有缺陷：`build_dataset_v5_5.py` 有 6 個類別指回 `Datasets_YOLO26_v5r`，
即使 v5.5 自己的樹裡就有位元相同的副本。**v5.6 只讀自己的來源樹**，
重現時不必同時保留兩個版本的資料夾。

`_provenance.json`（8,066 筆）記錄每一張輸出影像的來源 md5、v5.5 所屬 split、
合成類型與所用 profile——驗收的 Gate 3/4/5/7 都建立在它上面。
