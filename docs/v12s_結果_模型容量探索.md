## 1. 判準裁決：**未通過**

```
預先登記的達標線   test mAP50 ≥ 0.83959   （v11.5 的 0.80959 + 0.03）
實得               test mAP50 =  0.81266
Δ vs v11.5                     = +0.00307
```

**3.84 倍的參數量只換到 +0.003 的 mAP50。**

達標線是 +0.03，而實得是 **+0.003 —— 只有門檻的十分之一**，
更關鍵的是它**遠低於本專案量過的 run 間全距 0.021**。
也就是說，這個差距與「同一個設定重跑一次」的隨機變異無法區分。

### 為什麼門檻訂在 0.03

這是**開跑前就寫死在 notebook cell 1 裡**的，不是事後決定的：

- per-class 雜訊地板實測 **±0.04**（v11 上，資料完全沒動的五個類別也移動這麼多）
- 三版（v10 / v11 / v11.5）在完全同一批影像上的 run 間全距 **0.021**

低於 0.03 的差距無法與雜訊區分，所以事先就約定那不算數。

## 2. 結論：**容量不是瓶頸**

這是本輪要回答的問題，答案很明確。

| 指標 | v11.5 | v12s | Δ | 判讀 |
| --- | ---: | ---: | ---: | --- |
| test mAP50 | 0.80959 | 0.81266 | **+0.0031** | 雜訊內 |
| test mAP50-95 | 0.60691 | 0.61836 | **+0.0115** | 雜訊內 |
| valid mAP50 | 0.82899 | 0.83652 | +0.0075 | 雜訊內 |
| valid mAP50-95 | 0.63580 | 0.64345 | +0.0077 | 雜訊內 |

### 逐類：九類裡只有一類的變化超過雜訊地板

| 類別 | v11.5 | v12s | Δ | 判讀 |
| --- | ---: | ---: | ---: | --- |
| **Scale_Insect** | 0.6704 | 0.7112 | **+0.0408** | **可辨識** |
| Thrips_Damage | 0.4515 | 0.4885 | +0.0371 | 雜訊內 |
| Canker | 0.8677 | 0.9016 | +0.0340 | 雜訊內 |
| Thrips | 0.7795 | 0.7526 | −0.0268 | 雜訊內 |
| Oily_Spot | 0.9446 | 0.9204 | −0.0242 | 雜訊內 |
| Citrus_Leaf_Miner | 0.6764 | 0.6523 | −0.0241 | 雜訊內 |
| Black_Spot | 0.9534 | 0.9486 | −0.0048 | 雜訊內 |
| Aphid | 0.9478 | 0.9436 | −0.0042 | 雜訊內 |
| Sooty_Mold | 0.9950 | 0.9950 | +0.0000 | — |

**九類裡有四類變差、四類變好、一類不動**，而且只有 `Scale_Insect` 一項
勉強越過 ±0.04 的雜訊地板。這個分佈本身就是「沒有系統性改善」的樣子 ——
若容量真的是瓶頸，應該看到多數類別同向改善，尤其是最弱的那幾類。

> **`Citrus_Leaf_Miner` 反而變差 0.024。** 它是九類裡第二弱的（0.65），
> 如果模型容量不足，它應該是最先受益的類別之一。它沒有。

### 這與先前的證據一致

模型端的改動至此**連續四輪無效**：

| 輪次 | 改動 | 結果 |
| --- | --- | --- |
| v9 六臂 | W-I-MPDIoU ×2、ADown、StarTripletBlock、imgsz 800 | **零臂通過 2σ** |
| v10 → v11 → v11.5 | 三次訓練協定與資料切分調整 | 同一批影像上全距 **0.021**（= 雜訊） |
| **v12s** | **模型尺度 3.84× 參數** | **+0.003（= 雜訊）** |

唯一真正有效過的手段仍然是**資料端的標註重整**
（v5 → v5r：Thrips AP50 從 0.572 → 0.749，用的是原封不動的官方架構）。

## 3. 成本

| | v11.5 | v12s | 倍率 |
| --- | ---: | ---: | ---: |
| 參數量 | 2.52 M | 9.67 M | 3.84× |
| GFLOPs | 7.65 | 26.67 | 3.49× |
| 訓練時間 | 3.06 h | 4.91 h | **1.61×** |
| **平台 1 推論延遲（推估）** | **266 ms** | **約 950 ms** | **3.5×** |

**訓練成本只有 1.61×，比 GFLOPs 的 3.49× 低很多** ——
代表在 n 尺度時 GPU 並未吃滿，資料管線是相當大的固定成本。

但**推論端沒有這個緩衝**：依 v12.1 在平台 1 的實測（延遲與 GFLOPs 幾乎成正比，
640→320 實測 4.11× vs 理論 4.05×），s-p2 推估約 **950 ms/張 ≈ 1.05 FPS**。

> ### ⚠ v12s 不是候選部署模型
>
> 平台 1 上連 n 尺度的 266 ms 都離 30 FPS 差 6.8 倍，s 尺度只會更遠。
> **v12s 的定位是「精度上限探索」——回答容量是不是瓶頸，答案是不是。**
> 它不應該出現在任何部署選項的清單裡。

## 4. 附帶確認的三件事

### 4.1 `patience=0` + `last.pt` 的協定再次成立

| | `best.pt` | `last.pt` | 差距 |
| --- | ---: | ---: | ---: |
| test mAP50 | 0.81294 | 0.81266 | **0.00028** |
| test mAP50-95 | 0.61902 | 0.61836 | 0.00066 |
| valid mAP50 | 0.83634 | 0.83652 | −0.00018 |

差距全部 ≤ 0.0007，且方向不一致 —— 與 v11.5 的結論相同：
**`best` 與 `last` 沒有可辨識的差異，用無選擇偏誤的 `last.pt` 不用付代價。**

`best.pt` 高出平台期僅 **+0.00241 = 0.77σ**，是歷來最小
（v10 2.8σ、v11 2.7σ、v11.5 1.5σ）。

### 4.2 評估精度維持達標

pooled ±2SE 最差 **0.099**（`Citrus_Leaf_Miner`），九類全部 ≤ 0.10。
v5.6 的招牌目標在 v12s 上依然成立。

### 4.3 `batch=20` 沒有 OOM

Step.4 的顯存探測通過，訓練全程沒有降 batch。
**所以本輪確實是純粹的尺度比較，沒有額外變因。**

## 5. 我在計畫階段預測錯的兩件事

照實記錄，因為它們會影響往後的估算方式。

### 5.1 預測「最佳輪次會比 ep53 更早」——錯了

我在 notebook cell 1 寫：

> 「v11.5 的 `val/cls` 在 ep39 就見底，而 raw train 只有 2,353 張。
> 參數放大 3.84× 在同樣的資料上，預期最佳輪次比 ep53 更早。」

**實際最佳輪次是 ep69，比 v11.5 的 ep53 更晚。**
而且 `last.pt` 相對平台期是 **+0.00313**（不是負的），完全沒有過擬合的跡象。

計畫裡因此寫了一條「若 `last.pt` 明顯劣於平台期，要重新檢視它的正當性」的但書 ——
**那個情況沒有發生**，`last.pt` 照常可用。

順帶一提，ep69 這個數字很眼熟：**v8、v9/A0、v11 的最佳輪次也都是 ep69。**

### 5.2 時間估太多

我估 **7.6–9.1 小時**，實際 **4.91 小時**。

錯在我拿 GFLOPs（3.49×）線性外推訓練時間，但**資料管線是固定成本**，
在 n 尺度時 GPU 並沒有吃滿。實際的訓練時間倍率只有 **1.61×**。

> **往後估訓練時間不要用 GFLOPs 外推。** 那個方法在推論端成立
> （v12.1 實測延遲與 GFLOPs 幾乎成正比），但在訓練端會高估，
> 因為資料載入與增強不隨模型放大。

## 6. 下一步

### 6.1 這個結論指向哪

既然容量不是瓶頸，**預算應該移回資料端**。九類裡最弱的三個是：

| 類別 | AP50 | 已知成因 |
| --- | ---: | --- |
| **Thrips_Damage** | 0.489 | **框定義不一致**（valid/test 差 0.202，三輪都沒收斂）→ 人工工作包 A |
| Citrus_Leaf_Miner | 0.652 | 樣本量少（raw 111 張）→ 人工工作包 B（外部 150 張補標） |
| Scale_Insect | 0.711 | 分佈問題，v12s 唯一改善的一類 |

**工作包 A 與 B 目前都還沒發出去**（回收端 0 個檔案）。
在容量已被排除的情況下，這兩件事變成剩下最有機會的手段。

### 6.2 不要再做的

- **不要試 m 尺度。** s 尺度 3.84× 參數只換到雜訊等級的差異，
  m 尺度（21.07 M / 90.34 GFLOPs）沒有理由會不同，而訓練成本會再上去。
- **不要再從模型端找改善。** 連續四輪、共十一種改動全部無效。

### 6.3 若要突破部署延遲

與本輪無關，但值得一併記著（依 v12.1 的結論）：
**QAT** 或**直接在 320 解析度上訓練**是僅剩的兩條路，兩者都要重訓。
