## 0. 結論先講

**這是即時辨識功能的採用門檻。** 部署線再給最多兩週、最多一次重訓，期限是 2026-09-22 的週會：
**有組合過線，App 就採用即時辨識；沒有，就不採用即時辨識**，App 只做拍照辨識，部署線結案。

- **過線 = 三條同時成立**：手機延遲 ≤ 40 ms、test mAP50 ≥ 0.764、
  沒有任何一類比 `fp32@320` 掉超過 0.10（§2）。
- **先算上限，算不到就不跑。** 用 v12.1 的手機實測擬合出延遲模型（誤差 ≤ 1.5%），
  每條路先代入最好情況——**連最好情況都到不了 40 ms 的，不花任何成本就關掉**。
  這一步關掉了 QAT、NCNN/MNN、拿掉 P2 頭（§3）。
- **剩下值得跑的只有 5 個匯出組合，全部不用重訓**（第一階段，約一小時）。
  只有「延遲過了、精度差一點」時才開第二階段的那一次重訓（§4）。

## 1. 為什麼現在需要止損

**教授的說法是「達不到某個標準，就不要採用即時辨識的功能」。** 所以這份標準是兩件事合一：
它是**功能的採用門檻**（過線才做即時辨識），也是**測試的止損點**（到期沒過就不再找）。
沒過線的後果不是專案失敗，而是 App 少一個功能、只做拍照辨識——這條退路本來就可行（§5）。

v12.1 之前的每一步都很便宜：匯出一個組合幾十秒、量一次手機幾分鐘。
**剩下的路成本高一個量級**——要嘛要重訓（每次約 3 GPU 小時，外加使用者的時間），
要嘛要自建工具鏈（NDK 交叉編譯、自寫 QAT）。這種線沒有止損就會一直延伸，
而它擠壓的是另一條更該做的線：**資料端的人工工作包 A / B 已經掛了兩週多，至今仍未發派**（§8）。

止損標準要回答三件事，本文件依序處理：

1. **怎樣算成功**（§2）——成功就停，不再往下優化
2. **哪些路值得試**（§3）——先用已量到的數字算出每條路的上限
3. **試到什麼時候為止**（§4）——預算與期限

## 2. 過線標準（三條都要過）

| # | 條件 | 門檻 | 依據 |
| --- | --- | --- | --- |
| L | **延遲** | 手機 CPU-only 4T、`num_runs=25`，**重複輪次的最小值 ≤ 40 ms** | 30 FPS −5 的上緣。比 28.6 ms 更快不算失格（`run_mobile_benchmark.py` 的 `meets_target` 會把過快也標 ✗，判準不沿用那個欄位） |
| | 　└ `end2end=False` 的圖 | 另加 **2 ms** 後處理保留 | 這種圖不含後處理，NMS 要在 App 端自己做。圖內 topk 在 320 實測佔 1.6 ms（66.4 vs 64.8），進位成 2 |
| A | **精度** | v5.6 test（401 張）上的 tflite **mAP50 ≥ 0.764** | = 現在就能交付的 `fp32@320`（0.78511）− run 間全距 0.021。**比現行交付物差到超過一次重跑的隨機變異，就是在用精度換速度，不是免費的** |
| C | **逐類** | 任一類 AP50 **比 `fp32@320` 低超過 0.10** 即否決 | 平均值會藏住單一類別崩掉。`Scale_Insect` 從 640 到 320 已經從 0.679 掉到 0.549（−0.131），再降解析度最先垮的就是它。0.10 = v5.6 評估集設計的解析度（±2SE ≤ 0.10） |

**延遲的量測協定**（不符合的數字不算數）：

- **判「通過」一輪就夠**：干擾只會讓數字變大，單輪 ≤ 40 ms 代表乾淨的值只會更小。
- **判「未過」要 ≥ 3 輪交錯**（`--repeat 3`），或單輪的數字就算扣掉實測最大散佈 39% 仍超過 40 ms。
  兩者都不滿足的標為「需補量」，不能拿來下結論。
- **帶 `--extra-flags` 的量測不算**同一個組合（判準程式會略過）。

逐類的參照值取 `fp32__i320__e2e1__md100`——那是 320 的組合裡唯一存了逐類 AP50 的一筆
（與 `e2e0` 的整體 mAP50 只差 0.005）。九個參照值已寫進判準程式。

## 3. 上限檢驗：先算最好情況，算不到就不跑

### 3.1 延遲模型

把 v12.1 的 12 個手機實測點（三種圖 × 四個解析度）對像素數做線性擬合，
s = (imgsz / 640)²：

| 圖 | 擬合式（ms） | 最大誤差 | 讀法 |
| --- | --- | ---: | --- |
| `fp32` ＋ `end2end=True` | **266.8 × s** | **0.6%** | 延遲與像素數**完全成正比**，沒有固定開銷 |
| `int8`（`end2end` 被強制關） | **8.6 + 138.0 × s** | 1.5% | 有約 **8.6 ms 的固定開銷** |
| `fp32` ＋ `end2end=False` | −9.3 + 283.8 × s | 4.9% | 640 那一點偏高（熱漂移），擬合較差；320–512 實測比 `e2e1` 快 2–3% |

第二列解釋了一件先前沒講清楚的事：**INT8 的加速比隨解析度下降而縮小**。
對同樣 `end2end=False` 的 fp32，640 是 1.88×、512 是 1.75×、416 是 1.63×、**320 只剩 1.49×**。
v12.1 引用的「1.81×」是 640 的數字，**在真正需要的低解析度不成立**——
固定開銷不隨解析度縮小，解析度越低它佔的比例越大。

### 3.2 各解析度的最好情況

| imgsz | `fp32` e2e1 | `int8`（含 2 ms 保留） | ≤ 40 ms？ |
| ---: | ---: | ---: | --- |
| 320 | 66.4（實測） | 45.5（實測 43.5） | 都不行 |
| 288 | 54.0 | **38.6** | 只有 int8 |
| 256 | 42.6 | **32.7** | 只有 int8 |
| 224 | **32.6** | **27.5** | 都行 |

**`fp32` 要降到 224 才進得了 40 ms。** 256 差 2.6 ms，而這條擬合的誤差只有 0.6%，所以不列為候選。
（imgsz 必須是 32 的倍數，224 與 256 之間沒有別的選擇。）

### 3.3 剩下的每一條路

| 路線 | 最好情況 | 成本 | 判定 |
| --- | --- | --- | --- |
| **`fp32` 直接降到 224**（不重訓） | 32.6 ms ✓；精度未知 | 匯出＋手機，分鐘級 | ✅ **第一階段** |
| **`int8` 降到 288 / 256 / 224**（不重訓） | 38.6 / 32.7 / 27.5 ms ✓；精度未知 | 同上 | ✅ **第一階段**。PTQ 的精度對解析度**不單調**（416 的 0.728 < 512 的 0.777），不能外推，三個都量 |
| **`--xnnpack_force_fp16`** | 取決於 CPU 有沒有 FP16 算術 | 一條指令 | ⚠ **先驗條件**：`/proc/cpuinfo` 的 Features 裡**沒有 `asimdhp` 就直接關**，有才量一輪。SM6115 的 Kryo 260 是 ARMv8.0 世代的核心，預期沒有 |
| **原生低解析度重訓**（在 224 上訓練） | 延遲同 `fp32@224`；精度可能補回降解析度的一部分損失 | 1 次 Kaggle 重訓（約 3 GPU 小時；資料管線是固定成本，低解析度不會等比例變快） | ⚠ **第二階段，有條件**（§4.2） |
| **QAT** | **@320 = 43.5 ms** ✗——QAT 產出的是同一種 INT8 圖，延遲與靜態 INT8 相同。⚠ 這個數字目前**只有單輪**，依 §2 的協定還不能判「未過」，第一階段補量 3 輪確認（四個解析度的擬合誤差只有 1.5%，預期不會翻盤） | 數天：ultralytics 8.4.121 **沒有任何 QAT 程式碼**（全庫搜尋 0 筆），紅線 R2 又禁止升版，只能自己寫 | ❌ **本預算不做**。@320 連上限都到不了；@288 以下 INT8 相對 fp32 只剩 1.3–1.5× |
| **NCNN / MNN** | 要比 `fp32@320` 快 **1.62×** 才夠；框架之間通常差數十個百分點 | 半天以上（裝 NDK、交叉編譯） | ❌ **本預算不做**。@320 補不上；@224 TFLite 本身就預測會過，換框架不增加資訊 |
| **拿掉 P2 頭**（標準 `yolo26n`） | 桌機快 1.57× → @320 約 42.3 ms ✗，@288 約 34.4 ms | 1 次重訓 | ❌ **本預算不做**。@320 不過；@288 的精度沒有便宜的前測。P2 本來就是為小目標加的，而降解析度已經讓 `Scale_Insect` 掉 0.131——兩個都傷小目標的改動會疊在一起 |
| GPU / NNAPI / `w8a32` / `w8a16` / `max_det` | — | — | ❌ v12.1 已關，理由不變 |
| **第二台測試機** | 可能完全改變結論 | 需要硬體 | ⚪ **不屬於這條線的預算**。它改變的是問題本身，要另開 |

> **只把預算花在有便宜前測的路線上。** 保留原生低解析度重訓、不保留拿掉 P2 頭，
> 差別不在哪條比較有希望，而在前者能先用第一階段的數字判斷值不值得，後者不能。

## 4. 預算與停損點

### 4.1 第一階段：不重訓（目標 2026-09-15 週會前）

| 項目 | 內容 |
| --- | --- |
| 匯出 | `fp32` @224（`e2e1`、`e2e0` 各一）＋ `int8` @288 / 256 / 224，共 **5 個**，全部 `--val` |
| 量測 | 5 個 × `--repeat 3`，CPU-only 4T；另補 **`int8@320` × 3 輪**（不是候選，是為了讓 §3.3 關掉 QAT 的那一格有 3 輪的依據） |
| 先驗 | `/proc/cpuinfo` 查 `asimdhp` |
| 成本 | 0 GPU 小時。需要使用者**開 Docker Desktop、接上手機並解鎖**，其餘約一小時 |

**先量精度、後量延遲。** 精度在桌機的容器裡就能量完。若 5 個的 mAP50 都低於
0.764 − 0.032 = **0.732**，連手機都不用接，第一階段直接結束。

### 4.2 第二階段：最多一次重訓（期限 2026-09-22 週會前）

**准入條件**：第一階段有 `fp32` 組合**延遲已過、mAP50 落在 [0.732, 0.764)**。

- 差距上限 0.032 = 本模型 640 → 320 的整段損失（PyTorch 0.80897 → 0.77663）。
  原生低解析度重訓最多只能補回「訓練與推論解析度不一致」的那一份，
  **要它補回比整整一次解析度減半還多的損失，不合理**。
- 准入就訓一次，在准入的那個解析度上訓練，協定照舊（`patience=0`、固定輪數、報 `last.pt`）。
  **未過就結案，不再調超參數重訓第二次。**
- `int8` 的組合即使「差一點」也不准入：它要補的是量化誤差，那是 QAT 的事，不在本預算。
- 重訓後的權重匯出前要**先改檔名**（例：`v12_2_i224.pt`）：`export_tflite.py` 用權重檔名當前綴，
  沿用 `last.pt` 會和 v11.5 的產物撞名。

### 4.3 三個停損點（任一觸發即停）

| # | 條件 | 結果 |
| --- | --- | --- |
| **S1** | 有組合過線 | **採用即時辨識**，用過線組合中 mAP50 最高者。停止搜尋，不再往下優化 |
| **S2** | 第一階段全部未過且沒有組合准入第二階段，或第二階段那一次重訓仍未過 | **不採用即時辨識**，結案 |
| **S3** | **2026-09-22** 週會 | 無論做到哪裡都**不採用即時辨識**、結案。沒做完的項目關掉，不延到下一週 |

`tools/judge_deploy_stoploss.py` 會自動判 S1、S3 與第二階段准入；
S2 需要知道第二階段有沒有跑過，程式只提示、由人判斷，且**第一階段的 5 個組合沒匯出完之前不提示 S2**。
v12.1 已關的變體（`w8a16`、`w8a32`）在程式裡明寫為「已關」——
它們的關閉理由在 v12.1 的文字分析裡，量測 JSON 中 `w8a16` 只有一筆「無結果」，
不明寫的話會被誤判成「還沒量、值得量」。

## 5. 停下來之後

**若有組合過線（S1）→ 採用即時辨識**，用過線組合中 mAP50 最高者。
後續的整合工作不屬於搜尋：`end2end=False` 的組合要在 App 端實作 NMS，
並實測後處理有沒有落在 2 ms 的保留之內。

**若沒有組合過線（S2 / S3）→ 不採用即時辨識，App 只做拍照辨識**（對準 → 拍照 → 出結果）：

- 部署線結案，寫一份結案報告：「在平台 1 上，YOLO26n-P2 達不到即時辨識的門檻」，
  附已試過的路與各自的上限
- **拍照模式不受 40 ms 限制，所以用哪一顆模型要重新選。**
  v12.1 建議 `fp32@320`，是站在「要追 30 FPS」的前提上；不做即時辨識，就沒有理由為速度付 0.03 mAP50。
  這不屬於止損標準的範圍，是另一個待定的決定：

  | 候選 | 延遲 | mAP50 | 大小 | 取捨 |
  | --- | ---: | ---: | ---: | --- |
  | `fp32@320` ＋ `e2e0`（v12.1 的建議） | 64.8 ms | 0.785 | 9.54 MB | 最快，但速度在拍照模式裡用不到；App 要自己做 NMS |
  | `fp32@640` ＋ `e2e1` | 266.3 ms | 0.816 | 9.85 MB | 最準；0.27 秒在拍照流程中體感可接受（v12 §5.3）；圖內含後處理 |
  | `w8a32@640` ＋ `e2e1` | 279.5 ms | 0.819 | **3.10 MB** | 精度同上，檔案小 3 倍 |

  **要團隊先給拍照模式一個延遲上限**（例如「按下快門後幾秒內出結果」），才能在這三者之間選。
- **這條線只在前提改變時重開，且要另寫計畫**：有第二台測試機（中階以上 SoC），
  或願意投入 QAT 的工程量

```bash

.venv/Scripts/python.exe tools/judge_deploy_stoploss.py
```

## 8. 與資料線的關係

- 資料線**不需要新的止損標準**——它的判準早就登記了：
  工作包 A 看兩人的中位 IoU（≥ 0.85 全類重標，否則刪除該類別），
  工作包 B 走 `--arm ext` 與 base 做 2σ 比較。
- **它缺的是發派，不是判準。** 兩包自 2026-09-05 就已備妥
  （A 20 張、B 150 張，在 `Datasets/1_原始影像/_人工標註待辦/`），
  回收端到 2026-09-11 仍是 **0 個檔案**。
- 部署線的預算刻意壓在「最多兩週、最多一次重訓」，就是為了不跟 A / B 搶使用者的時間。
