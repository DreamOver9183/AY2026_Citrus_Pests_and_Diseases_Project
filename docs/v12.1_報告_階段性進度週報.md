## 摘要

- **本期把專案缺的另一半量尺補上了。** 到 v11.5 為止只量得出**精度**
  （九類 ±2SE ≤ 0.10），完全量不出**延遲**——所以「要不要換更大的模型」
  一直無法討論，因為沒有預算可以花。現在兩邊都量得到。
- **主結論：測試平台 1 達不到 30 FPS，任何官方匯出參數的組合都不行。**
  最快的組合是 43.5 ms（23.0 FPS）但精度不可用；
  **精度可用的最佳是 `fp32 @ 320` 的 64.8 ms（15.4 FPS），相對 640 只掉 0.032 mAP50。**
- **把官方匯出文件的參數表整份測過**：22 個組合量了完整 mAP、18 個量了手機延遲，
  另加 4 種匯出格式。過程中找到**文件與實際不符的四處**（§4）。
- **與 7 月的手動實機紀錄交叉驗證，同一台手機、相隔兩個月，
  int8 的延遲吻合到 1.2% 以內**（§5）。同時發現該紀錄的彙整表有**兩列**數據
  與它自己附的原始 log 不符，其中一列正好是整份報告摘要的第一句結論；**已更正並推送**。
- **v12s 已訓練完畢，判準未通過** —— 3.84 倍參數只換到 **+0.003** mAP50（門檻 +0.03）。
  **結論：容量不是瓶頸**，預算應移回資料端（§6）。

## 0. 全案盤點：進度 / 問題 / 解決方案

> 本節是**跨週的累積狀態**，不限於本期。本期的細節從 §1 開始。

### 0.1 三條線的進度

專案實際上是三條可以分開推進的線。**它們的成熟度差很多，混在一起講會失焦。**

| 線 | 版本演進 | 現況 | 成熟度 |
| --- | --- | --- | --- |
| **① 資料集** | v5 → v5r → v5.5 → **v5.6** | 9 類，train 7,264 / valid 401 / test 401。**九類 pooled ±2SE 全部 ≤ 0.10**（最差 0.099），全類別零跨 split 近重複，框膨脹缺陷已修 | **量尺已達標**，但兩個類別的**標註品質**仍是開放問題 |
| **② 模型** | v8 → v9（六臂）→ v10 → v11 → v11.5 → **v12s** | 交付基準是 **v11.5**（test mAP50 0.80959 / mAP50-95 0.60691）。訓練協定已固定為 `patience=0` + 固定輪數 + 報 `last.pt` | **已走到底**：模型端連四輪、共十一種改動全部無效 |
| **③ 部署** | **v12 → v12.1**（本期新開） | 平台 1 = OPPO CPH2641 / Snapdragon 662。22 組量完整 mAP、18 組量手機延遲、4 種匯出格式。**最佳可用組合 `fp32 @ 320` = 64.8 ms / 15.4 FPS / mAP50 0.785** | **量清楚了**：官方參數已窮盡，**達不到 30 FPS** |

**本期最大的結構性變化是第三條線從無到有。**
在此之前專案只有精度這一把尺，沒有延遲那一把 ——
所以「要不要換更大的模型」根本無法討論，因為不知道預算有多少。
現在兩把尺都在，也才能明確地說出「v12s 不是部署候選」這種話。

### 0.2 問題 → 解決方案（全案累積）

**已解決的**，按發生順序：

| # | 問題 | 根因 | 解決方案 | 代價 / 收穫 |
| --- | --- | --- | --- | --- |
| 1 | **續跑會靜默毀掉權重** | ultralytics 8.4.121 的 `resume=True` 把權重換成 COCO 預訓練 | 建立辨識法（可續跑的 ckpt 約 15.9 MB，被 `strip_optimizer` 過的只有 5.6 MB），改由 `epochN.pt` 續跑 | 專案史上最貴的一個坑，已實戰驗證修好 |
| 2 | **P3 歸因錯誤** | 原本認定是「小目標定位精度」，其實是**框定義不一致** | 逐框量測（避開 EXIF／多邊形／夾取三個陷阱） | 歸因更正，方向從架構改動轉向標註 |
| 3 | **近重複影像跨 split 洩漏** | 同一株植物連拍／多角度被切到不同 split（三個 Pests 類共 13.4%） | 近重複群組**整群移進 train**，不刪圖 | 全類別零洩漏；v8 的歷史數字因此作廢 |
| 4 | **評估集太小，valid 與 test 互相矛盾** | 每類每 split 只有 20–25 張（`Scale_Insect` 兩邊差 0.308，遠超門檻） | v5.6：推翻「train 不能縮水」這條沒被檢驗的前提，把既有影像移進評估集 | **沒有新拍任何一張照片**就達標，代價僅 raw train −6.0% |
| 5 | **增強讓標註框系統性脹大** | `Affine(rotate=±15°)` 取外接矩形，面積脹 1.075–1.300 倍；膨脹最嚴重的正是定位最差的類別 | 改用 `RandomRotate90`；邊界填充 `REFLECT_101` → `REPLICATE` | 九類的框面積比全部回到 1.000 |
| 6 | **`best.pt` 有選擇偏誤** | best 由 valid 挑出 → valid 不能併入評估 | 協定改為 `patience=0` + 固定輪數 + **報 `last.pt`** | ±2SE 從 0.140 降到 0.099，**而且訓練時間更短**；實測 best 與 last 沒有可辨識差異 |
| 7 | **量不出延遲** | 專案只有精度量尺 | 合併 `Benchmark/` 工具鏈（同 repo）＋ 三支自製 driver | 部署討論從推測變成量測 |
| 8 | **LiteRT 匯出在 Windows 被擋** | `export_litert` 第一行是平台斷言 | 進 `linux/amd64` Docker 容器 | 順帶排除 ONNX → saved_model 那條 numpy 相依死路 |
| 9 | **`adb push` 回報成功但檔案不在裝置上** | Git Bash 的 MSYS 改寫了裝置端路徑 | `MSYS_NO_PATHCONV=1`＋用 `adb shell ls` 實際驗證，不相信 push 的回報 | 已寫進工具，不會再踩 |
| 10 | **INT8 校正集只抽到單一類別** | `fraction` 是**排序後取前 N**，不是隨機抽樣；本專案檔名帶類別前綴 → 363 張全是 Aphid | 改為類別平衡校正（每類 60 張） | 缺陷是真的，但**修好後結果更差**（−0.143 vs −0.118）→ 原結論「靜態 INT8 不可用」仍成立 |
| 11 | **手機延遲被熱漂移汙染** | 連續量測時機身升溫，同組散佈可達 39% | 交錯重跑、**取重複輪次的最小值**（熱尖峰只會讓數字變大），散佈 >10% 就標記 | 數據可重現 |

**已判定、不再投入的**（結論本身就是產出）：

| 方向 | 判定 | 依據 |
| --- | --- | --- |
| **模型架構／損失改動** | 無效 | v9 六臂**零臂通過 2σ**，且「改動越貴結果越差」 |
| **訓練協定與切分微調** | 無效 | v10 / v11 / v11.5 在同一批影像上全距 0.021 = run 間變異 |
| **模型容量** | **不是瓶頸** | v12s：3.84× 參數 → **+0.003**（門檻 +0.03） |
| **GPU delegate / NNAPI** | 無效 | 即使 100% 委派仍比 CPU 慢；裝置只有 `nnapi-reference`，無加速器 |
| **量化加速** | 無效或不可接受 | `w8a32` 只省體積不省時間；`w8a16` 慢 27 倍；靜態 INT8 快 1.81× 但掉 0.143 mAP |
| **`close_mosaic`** | 幫倒忙 | v9 / v10 / v11 / v11.5 四次確認 |
| **影像剪接 / 圖片生成 / 外部資料集** | 已否決 | 方框剪貼會產生空框；生成圖仍須人工標；全世界找不到附框的柑橘潛葉蛾／薊馬偵測資料集 |

## 2. 主線：建立部署端的量尺

### 2.1 在此之前的狀態

專案有一個**明確的部署目標**（30 FPS ±5 = 每張 28.6–40 ms），
但**從來沒有量過**。所有「這個模型能不能上手機」的討論都建立在推測上。

### 2.2 建立了什麼

| 項目 | 內容 |
| --- | --- |
| `Benchmark/` | 由 `TFLite_Benchmark_skills` 合併進來（同 repo，非 submodule），含 ADB 與 benchmark APK，clone 即可用 |
| `Benchmark/export/` | `.pt` → `.tflite` 的 Docker 管線。ultralytics 的 LiteRT 匯出在 Windows 被平台斷言擋住，必須進 `linux/amd64` 容器 |
| `tools/export_tflite.py` | 四軸掃描（量化 × 解析度 × end2end × max_det），含逐框驗收與完整 mAP |
| `tools/run_mobile_benchmark.py` | 推送 → 執行 → 解析 logcat → 出報告，可重複執行 |
| `tools/export_other_formats.py` | ONNX / TorchScript / MNN / NCNN |

**匯出正確性已驗證**：fp32 與 w8a32 在完整 401 張 test 上的 mAP50 分別是
0.81554 / 0.81936，與 PyTorch 的 0.80897 差距都在 run 間雜訊（0.021）之內。
**`end2end=True`（NMS-free）的 YOLO26 可以經 LiteRT 直轉且不掉精度** ——
這在動工前是最大的未知數。

### 2.3 第一次量測的結果

平台 1 = **OPPO CPH2641 / Snapdragon 662 (SM6115) / Adreno 610 / Android 14**，
2020 年的入門級 SoC。

六組設定全部未達標，最快 272 ms（3.68 FPS），**離目標差 6.8 倍**。

## 3. 官方匯出參數全面掃描

### 3.1 有效的槓桿只有一個

| 手段 | 加速 | 精度代價 | 判定 |
| --- | ---: | ---: | --- |
| **`imgsz` 640 → 320** | **4.11×** | **−0.032** | ✅ **唯一有效** |
| `quantize=8`（靜態 INT8） | 1.81× | −0.143 | ❌ 精度不可接受 |
| `end2end=False` | 1.02–1.05× | 無 | ✅ 小幅但一致，免費 |
| `max_det` 300 → 50 | 無 | 無 | ⚪ 免費但無益 |
| `quantize='w8a32'` | 無 | 無 | ⚪ 體積 3.18×，速度無益 |
| `quantize='w8a16'` | **0.037×（慢 27 倍）** | 無 | ❌ XNNPACK 無 INT16 核心 |
| GPU delegate | **0.96×（更慢）** | — | ❌ 即使 100% 委派 |
| NNAPI | 無（裝置無加速器） | — | ❌ |

### 3.2 精度 × 延遲的前緣

| 組合 | ms | FPS | mAP50 | 達標 |
| --- | ---: | ---: | ---: | :-: |
| `int8 @ 320` | **43.5** | 22.98 | 0.719 | ✗ |
| **`fp32 @ 320` + `e2e0`** | **64.8** | **15.42** | **0.785** | ✗ |
| `int8 @ 416` | 67.4 | 14.83 | 0.728 | ✗ |
| `fp32 @ 416` | 109.9 | 9.10 | 0.815 | ✗ |
| `fp32 @ 640` | 266.3 | 3.76 | 0.816 | ✗ |

**關鍵對照**：在**相同延遲**下，`fp32 @ 320`（64.8 ms / 0.785）
勝過 `int8 @ 416`（67.4 ms / 0.728）。
**對這個模型，計算預算該花在降解析度，不是量化** —— 與一般直覺相反。

這是本輪最有轉用價值的部分 —— 每一項都附程式碼證據，見 v12.1 報告 §1–§5。

| # | 文件說 | 實際 |

## 5. 與 7 月手動紀錄的交叉驗證

本專題 7 月用 ADB 手動測過同一台手機並寫成報告
（`AY2026_Citrus_Pests_and_Diseases_Report` 的〈系統測試與評估〉）。
兩份數據**互相獨立**，方法相同（同一套 ADB 流程、同樣 4 threads / CPU only）。

| | 07-14 手動 | 本輪（09-07） | 差異 |
| --- | ---: | ---: | ---: |
| XNNPACK 節點 | 539/548 = 98.36% | 542/551 = 98.4% | 3 個節點 |
| 平均推論 | **145.53 ms** | **147.3 ms** | **1.2%** |
| Overall 記憶體 | 73.41 MB | 72.74 MB | 0.9% |

**相隔兩個月、不同工具鏈，落在 1.2% 內。** 本輪的量測方法可信。

另外 7 月量到的 `yolo26n_p2_fp16`（5.44 MB）是 284 ms，而本輪的 fp32（9.85 MB）是 266 ms
—— **FP16 檔案在 CPU 上並沒有比較快**，與本輪測到的 `w8a32` 現象一致
（XNNPACK 對這些格式仍做浮點運算，省的是體積不是算力）。

### 該份報告有兩列數據不符，已更正並推送

逐**欄**比對 §5 表格與它自己附的原始 log（`count=25` 與 `Memory footprint` 兩行）之後：

| 表格列 | 比對結果 |
| --- | --- |
| `yolo26n_p2_w8a32.tflite` | **10 欄全錯**，且此檔名在整份文件的原始 log 裡從未出現。該批次實際載入的是 **`best_int8.tflite`**：145.53 ms（6.87 FPS）、節點 539/548 = 98.36%、記憶體 54.29 / 73.41 MB |
| `ssd_mobilenetv3_large_fp16.tflite` | **10 欄中 8 欄錯**（僅 FPS 與差值是由錯誤欄位算出的自洽值）。其節點率 88.59% 是從 fp32 那一列抄來的，實為 431/461 = 93.49% |
| 其餘 6 列 | 與各自的 log 完全相符 |

`16530`、`50840`、`45470`、`123630`、`14730`、`20670`、`27570` 這些數字
在原始 log 中出現次數**全部是 0**。

第一列正是該報告摘要的第一句（「`yolo26n_p2_w8a32` 最快，16.53 ms、60.50 FPS」），
會讓人以為 60 FPS 已達成，而真實值是 **6.87 FPS**；
更正後全表最快的其實是 `ssd_mobilenetv3_small_fp32`（24.35 ms）。

## 6. v12s：容量不是瓶頸

`Train Code/v12s/train_v12s.ipynb` 已在 Kaggle 跑完 70 輪（4.91 h）。

### 判準裁決：未通過

```
預先登記的達標線   test mAP50 ≥ 0.83959   （v11.5 的 0.80959 + 0.03）
```

## 8. 下週

### 8.1 本期已把兩條路都走到底了

這一週同時關掉了兩個方向，而且都是**用預先登記的判準關的**，不是憑印象：

| 方向 | 結論 | 依據 |
| --- | --- | --- |
| **模型容量** | **不是瓶頸** | v12s：3.84× 參數 → +0.003（門檻 +0.03） |
| **部署端調參** | **達不到 30 FPS** | v12.1：22 組全未達標，最佳 15.4 FPS |

**所以下一步不在這兩條線上。**

### 8.2 需要在會議上決策的兩件事

1. **30 FPS 是不是真的需要？**
   若 App 的互動是「對準葉片 → 拍照 → 出結果」，65 ms 使用者不會察覺，
   `fp32 @ 320`（15.4 FPS / mAP50 0.785）**現在就可以交付**。
   若必須是即時串流，這台裝置做不到，要換硬體或換架構。
   **這是產品決策，技術面已經量清楚了。**

2. **人工工作包 A / B 要不要發？**
   容量既然已被排除，**資料端是目前唯一還沒試過的方向**。
   最弱的三類與其成因：

   | 類別 | AP50 | 成因 | 對應 |
   | --- | ---: | --- | --- |
   | `Thrips_Damage` | 0.489 | 框定義不一致（valid/test 差 0.202，三輪未收斂）；**2026-06 起就有類別代號但零標註，v5.5 才建立** | **工作包 A** |
   | `Citrus_Leaf_Miner` | 0.652 | 樣本量少（raw 111 張） | **工作包 B** |
   | `Scale_Insect` | 0.711 | 分佈問題 | v12s 唯一改善的一類 |

   > **新增依據（2026-09-08 盤點 `_History/` 得出）**：`Thrips_Damage` 對應 2026-06
   > 12 類資料集裡的 `P_TP_LD`，當時 **train / valid / test 全部零標註**。
   > 也就是說它不只是「標得不一致」，而是**九類裡唯一從零開始、且最晚建立的類別**。
   > 這讓工作包 A 的必要性更明確：要先確認這套標註約定本身站不站得住。

### 8.3 若決定要突破 15 FPS

只剩訓練端的兩條路，兩者都要重訓：

- **QAT（量化感知訓練）** —— 唯一可能拿到 INT8 的 1.81× 而不付 0.14 mAP 的方法
- **直接在 320 解析度上訓練**（而不是 640 訓練後降解析度推論）

### 8.4 明確不要再做的

- **不要試 m 尺度模型。** s 尺度的 3.84× 參數只換到雜訊等級的差異，
  m 尺度（21.07 M / 90.34 GFLOPs）沒有理由會不同，訓練與推論成本卻會再上去。
- **不要再從模型端找改善。** 連續四輪、共十一種改動全部無效。
- **不要再花時間在 GPU / NNAPI 上。** 兩者在平台 1 都已確定無效且理由清楚。

### 9.4 兩組指標來自不同的工作點

這是讀這張表最容易出錯的地方，必須寫清楚：

| 欄位 | 來源 | 信心閾值 |
| --- | --- | --- |
| mAP50、mAP50-95、Precision、Recall | ultralytics `val()` | **conf = 0.001** |
| Detection Jaccard、TP / FP / FN | 混淆矩陣 | **conf = 0.25** |

**同一列的 Precision 與 Jaccard 不是在同一個工作點上算出來的**，兩者不能互推。
以 v9 為例，同一顆權重在 conf = 0.4985 下的 Jaccard 是 0.67733（valid），
比 conf = 0.25 的 0.65353 高，但 mAP50 會從 0.86651 掉到 0.77299 ——
高閾值必然壓低 mAP。**引用時務必連同閾值一起講。**

Detection Jaccard 的定義是 $\sum \text{TP} / \sum(\text{TP} + \text{FP} + \text{FN})$，
略過物件偵測情境下人為約定的 TN，是比 Accuracy 更可信的整體正確率替代指標。
完整定義見 [通用_參考_評估指標與公式.md](通用_參考_評估指標與公式.md)。

### 9.6 為什麼舊版的數字最高卻不代表最好

v9 的 test mAP50 是 0.89079、2026-06 的 YOLO26-large 更高達 0.871（valid），
但都**不能拿來說「後來變差了」**。先講 v9 的三個原因：

1. **v5r 有 13.4% 的跨 split 近重複影像**（三個 Pests 類別），評估集裡有模型在訓練時看過的近乎相同的照片，**數字被灌水**。v5.5 起已全類別清零。
2. **v9 只有 8 個類別，沒有 `Thrips_Damage`。** 該類別是九類中最弱的一項（v12s 為 0.488），把它加進平均自然會把整體拉低。v10 在 v5.5 上取 8 類等效值是 0.864 / 0.658，與 v9 的 0.891 / 0.678 只差 0.02 至 0.027，而 v9 那側還受洩漏灌水 —— **實質接近持平，不是退步**。
3. **評估集本身換過。** v5.6 的 valid 與 test 各為 401 張，是為了把每個類別的評估誤差壓到 ±2SE 小於等於 0.10 而重新切分的；量尺變了，刻度就不能互換。

**2026-06/07 那六列還要再多兩個理由：**

4. **那是 12 類資料集，其中兩類零標註**（`P_AP_LD`、`P_TP_LD`），另有兩個健康葉類別（`H_MC`、`H_PK`）。
   健康葉相對容易，納入平均會把整體拉高；而 valid 只有 438 張、`P_SI` 一類就佔框數 68.8%。
5. **那些數字是最後一輪、卻被標成「最優」。** 實際峰值都更早（large ep55 = 0.882），
   四個模型被低估 0.009–0.015 mAP50 —— 連「當時究竟是多少」都要重新界定。

> **一句話**：這張表適合回答「某一版當時量到什麼」，不適合回答「哪一版比較強」。
> 跨資料集的強弱比較在本專題**沒有合法的基準**，唯一的例外是同資料集內的對照。
