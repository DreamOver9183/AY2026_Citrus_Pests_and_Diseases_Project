## 摘要

- **本期把專案缺的另一半量尺補上了。** 到 v11.5 為止只量得出**精度**
  （九類 ±2SE ≤ 0.10），完全量不出**延遲**——所以「要不要換更大的模型」
  一直無法討論，因為沒有預算可以花。現在兩邊都量得到。
- **主結論：測試平台 1 達不到 30 FPS，任何官方匯出參數的組合都不行。**
  最快的組合是 43.5 ms（23.0 FPS）但精度不可用；
  **精度可用的最佳是 `fp32 @ 320` 的 64.8 ms（15.4 FPS），相對 640 只掉 0.032 mAP50。**
- **把官方匯出文件的參數表整份測過**：22 個組合量了完整 mAP、18 個量了手機延遲，
  另加 4 種匯出格式。過程中找到**文件與實際不符的四處**（§4）。
- **與組員 7 月的手動實機紀錄交叉驗證，同一台手機、相隔兩個月，
  int8 的延遲吻合到 1.2% 以內**（§5）。同時發現該紀錄的彙整表有一列數據錯誤，
  而那一列正好是整份報告摘要的第一句結論。
- **v12s 訓練進行中**，判準已預先登記（§6）。

## 2. 主線：建立部署端的量尺

### 2.1 在此之前的狀態

專案有一個**明確的部署目標**（30 FPS ±5 = 每張 28.6–40 ms），
但**從來沒有量過**。所有「這個模型能不能上手機」的討論都建立在推測上。

### 2.2 建立了什麼

| 項目 | 內容 |
| --- | --- |
| `Benchmark/` | 由組員的 `TFLite_Benchmark_skills` 合併進來（同 repo，非 submodule），含 ADB 與 benchmark APK，clone 即可用 |
| `Benchmark/export/` | `.pt` → `.tflite` 的 Docker 管線。ultralytics 的 LiteRT 匯出在 Windows 被平台斷言擋住，必須進 `linux/amd64` 容器 |
| `tools/export_tflite.py` | 四軸掃描（量化 × 解析度 × end2end × max_det），含逐框驗收與完整 mAP |
| `tools/run_mobile_benchmark.py` | 推送 → 執行 → 解析 logcat → 出報告，可重複執行 |
| `tools/export_other_formats.py` | ONNX / TorchScript / MNN / NCNN |

**匯出正確性已驗證**：fp32 與 w8a32 在完整 401 張 test 上的 mAP50 分別是
0.81554 / 0.81936，與 PyTorch 的 0.80897 差距都在 run 間雜訊（0.021）之內。
**`end2end=True`（NMS-free）的 YOLO26 可以經 LiteRT 直轉且不掉精度** ——
這在動工前是最大的未知數。

### 2.3 第一次量測的結果

平台 1 = **OPPO CPH2641 / Snapdragon 662 (SM6115) / Adreno 610 / Android 14**，
2020 年的入門級 SoC。

六組設定全部未達標，最快 272 ms（3.68 FPS），**離目標差 6.8 倍**。

## 3. 官方匯出參數全面掃描

### 3.1 有效的槓桿只有一個

| 手段 | 加速 | 精度代價 | 判定 |
| --- | ---: | ---: | --- |
| **`imgsz` 640 → 320** | **4.11×** | **−0.032** | ✅ **唯一有效** |
| `quantize=8`（靜態 INT8） | 1.81× | −0.143 | ❌ 精度不可接受 |
| `end2end=False` | 1.02–1.05× | 無 | ✅ 小幅但一致，免費 |
| `max_det` 300 → 50 | 無 | 無 | ⚪ 免費但無益 |
| `quantize='w8a32'` | 無 | 無 | ⚪ 體積 3.18×，速度無益 |
| `quantize='w8a16'` | **0.037×（慢 27 倍）** | 無 | ❌ XNNPACK 無 INT16 核心 |
| GPU delegate | **0.96×（更慢）** | — | ❌ 即使 100% 委派 |
| NNAPI | 無（裝置無加速器） | — | ❌ |

### 3.2 精度 × 延遲的前緣

| 組合 | ms | FPS | mAP50 | 達標 |
| --- | ---: | ---: | ---: | :-: |
| `int8 @ 320` | **43.5** | 22.98 | 0.719 | ✗ |
| **`fp32 @ 320` + `e2e0`** | **64.8** | **15.42** | **0.785** | ✗ |
| `int8 @ 416` | 67.4 | 14.83 | 0.728 | ✗ |
| `fp32 @ 416` | 109.9 | 9.10 | 0.815 | ✗ |
| `fp32 @ 640` | 266.3 | 3.76 | 0.816 | ✗ |

**關鍵對照**：在**相同延遲**下，`fp32 @ 320`（64.8 ms / 0.785）
勝過 `int8 @ 416`（67.4 ms / 0.728）。
**對這個模型，計算預算該花在降解析度，不是量化** —— 與一般直覺相反。

## 4. 官方文件與實際不符的四處

這是本輪最有轉用價值的部分 —— 每一項都附程式碼證據，見 v12.1 報告 §1–§5。

| # | 文件說 | 實際 |
| --- | --- | --- |
| 1 | 參數表**沒有** `end2end` | 存在且 LiteRT 可用。它把 GPU 委派率從 9.7% 提到 100% |
| 2 | `max_det` 是「輸出保留的最大檢測數量」 | 對 end2end 模型**決定圖裡烘進去的 TopK k**（`exporter.py:1291`） |
| 3 | `quantize='w8a16'` 列為 LiteRT 支援 | 支援、精度無損，但**慢 27 倍** —— XNNPACK 一個節點都沒接手 |
| 4 | `fraction` 是「用於校正的資料集子集」 | **排序後取前 N**。本專案檔名帶類別前綴 → 抽到的 363 張全是 Aphid |

> 第 3 點值得單獨記住：**「文件說支援」不等於「實務上可用」。**

## 5. 與組員手動紀錄的交叉驗證

組員 7 月用 ADB 手動測過同一台手機並寫成報告
（`AY2026_Citrus_Pests_and_Diseases_Report` 的〈系統測試與評估〉）。
兩份數據**互相獨立**，方法相同（同一套 ADB 流程、同樣 4 threads / CPU only）。

| | 組員（07-14） | 本輪（09-07） | 差異 |
| --- | ---: | ---: | ---: |
| XNNPACK 節點 | 539/548 = 98.36% | 542/551 = 98.4% | 3 個節點 |
| 平均推論 | **145.53 ms** | **147.3 ms** | **1.2%** |
| Overall 記憶體 | 73.41 MB | 72.74 MB | 0.9% |

**相隔兩個月、不同人、不同工具鏈，落在 1.2% 內。** 本輪的量測方法可信。

另外組員量到的 `yolo26n_p2_fp16`（5.44 MB）是 284 ms，而本輪的 fp32（9.85 MB）是 266 ms
—— **FP16 檔案在 CPU 上並沒有比較快**，與本輪測到的 `w8a32` 現象一致
（XNNPACK 對這些格式仍做浮點運算，省的是體積不是算力）。

### ⚠ 該份報告有一列數據需要更正

`all_models_tflite_benchmark.md` 的這一列：

```
| yolo26n_p2_w8a32.tflite | ... | 16.53 ms | 60.50 FPS | ... |
```

逐列比對表格與它自己附的原始 log 之後：

- **`yolo26n_p2_w8a32.tflite` 這個檔名在整份文件的原始 log 裡從未出現**
- 該批次的 log 實際跑的是 **`best_int8.tflite`**，其值為
  **145.53 ms（6.87 FPS）**、節點 98.36%、記憶體 54.29 / 73.41 MB
- `16530` 這個微秒數在原始 log 中出現 **0 次**
- **其他每一列都與自己的 log 完全相符**（`yolo26n_fp16` 257.13 ✓、
  `yolo26n_p2_fp16` 284.02 ✓、四個 SSD 也都 ✓）

這一列正是該報告摘要的第一句（「`yolo26n_p2_w8a32` 最快，16.53 ms、60.50 FPS」），
會讓人以為 60 FPS 已達成，而真實值是 **6.87 FPS**。
更正後，兩份報告的結論一致：**這台手機上 YOLO26n-P2 不論哪種量化都在 145–300 ms。**

> 該 repo 屬於組員，**本輪未代為修改**，僅提供逐列比對結果。

## 8. 下週

### 8.1 立即（等 v12s 出來就做）

1. **判讀 v12s**，依預先登記的判準給結論。無論過或不過都是有用的結論：
   過 → 容量是瓶頸之一；不過 → 容量不是瓶頸，預算回資料端。
2. **v12s 的報告要標明它不是部署候選**（950 ms 推估）。

### 8.2 需要決策的（建議在會議上定）

3. **30 FPS 是不是真的需要？** 若 App 的互動是「對準葉片 → 拍照 → 出結果」，
   65 ms 使用者不會察覺，`fp32 @ 320` 現在就可以交付。
   若必須是即時串流，這台裝置做不到，要換硬體或換架構。
4. **人工工作包 A / B 要不要發**。`Thrips_Damage` 是九類中唯一未收斂的
   （valid/test 差 0.202，三輪都沒收斂），成因是框定義不一致，只能靠人工解。

### 8.3 若決定要突破 15 FPS

5. **QAT（量化感知訓練）** —— 唯一可能拿到 INT8 的 1.81× 而不付 0.14 mAP 的方法。
6. **直接在 320 解析度上訓練**（而不是 640 訓練後降解析度推論）。

兩者都要重訓，與 v12s 的容量探索是不同方向。**建議等 v12s 的結論出來再選**：
若 v12s 顯示容量不是瓶頸，那資源就該往資料端與部署最佳化走。
