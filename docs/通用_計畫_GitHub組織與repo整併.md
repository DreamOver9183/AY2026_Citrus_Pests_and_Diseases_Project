## 2. 提案：建組織，但**用「搬移」不是「重建」**

### 2.1 為什麼不開一個全新的 repo 重來

看起來「重新開始、結構乾淨」很吸引人，但代價很具體：

1. **報告庫的治理機制會歸零。** 上面那五項不是設定檔，是累積出來的規則與腳本。重建等於重做。
2. **CHANGELOG 裡的 commit hash 全部失效。** 那份紀錄逐筆對應到 git 歷史，換 repo 之後全都指向不存在的東西，可追溯性直接消失。
3. **git 歷史與作者紀錄會斷。** 誰在什麼時候改了什麼，全部查不到。

### 2.2 GitHub 的「轉移」功能可以避開以上全部

> **GitHub 的 repo transfer 會保留完整的 commit 歷史，並且自動建立永久轉址。**
> 已經寄給老師、寫在報告裡、印在海報上的舊網址**會自動跳到新位置**，不會 404。

所以「搬到組織」跟「開新 repo 複製檔案」是兩件完全不同的事。前者風險極低。

### 2.3 為什麼兩個 repo 不合併成一個

`Project` 的 `.git` 有 **678 MB**（因為訓練權重在版控裡），`Report` 只有 11 MB。

合併之後，**只想看報告的人（老師、評審、外系同學）也得先下載 678 MB**。而且兩者的規範完全不同：報告庫是純文件、有結構關卡；程式碼庫是程式與大檔。混在一起兩邊的規則都會失效。

**維持兩個 repo，各自獨立。**

## 6. 風險與對策

| 風險 | 可能性 | 對策 |
| --- | --- | --- |
| 舊網址失效 | 低 | GitHub 自動轉址；轉移後實際點一次舊網址確認 |
| 有人本機的 remote 沒更新 | 中 | 轉址仍可推拉，但仍請每人跑一次 `git remote set-url` |
| 轉移過程出錯 | 低 | 轉移是 GitHub 官方功能，不是手動複製；轉移前先確認兩邊都已 push |
| **展覽前動到東西出包** | **中** | **這是最實際的風險 → 見 §8 時程：只在展前做「加法」** |

## 8. 建議時程

**原則：專題展之前只做「加法」，不做「重排」。**

改結構的最壞時機就是展覽前 —— 它會吃掉本該花在 demo 與海報上的時間。

| 階段 | 做什麼 | 何時 |
| --- | --- | --- |
| **展前（必要）** | 確認 RAG／App 程式碼有進版控 | **最優先** |
| 展前（建議） | 建組織 → 轉移兩個 repo → 加一份寫著「一葉知病」的專案首頁 | 有空再做 |
| 展前（不做） | 改檔名、調目錄、統一兩個 repo 的命名規則 | **暫緩** |
| 展後 | 再評估要不要統一命名規則 | 展覽結束後 |

### 為什麼不建議統一兩邊的檔名規則

兩個 repo 現在各有一套命名慣例：

| | 慣例 | 例 |
| --- | --- | --- |
| Project `docs/` | `{範疇}_{類型}_{主題}` | `通用_參考_評估指標與公式.md` |
| Report | `<日期>_<模型代號>_<類型>` | `20260907_weekly_report.md` |

看起來不一致，但**兩邊各自內部一致，而且都有文件寫明理由**。要統一得改幾十個檔名、同步改寫上百條中文路徑連結 —— 而中文路徑連結壞掉是**靜默的**（本機正常，推上 GitHub 才 404，這正是報告庫要寫連結檢查腳本的原因）。

投入產出不成比例，**建議維持現狀**。

## 9. 執行步驟（三項都同意後才做）

1. 建立組織 `oneleaf-dx`，顯示名稱設為「一葉知病 OneLeaf」

6. 全員執行 `git remote set-url origin <新網址>`
7. 在組織首頁加一份專案介紹（`.github` repo 的 README）

**每一步都可逆，第 4 步之前隨時可以喊停。**
