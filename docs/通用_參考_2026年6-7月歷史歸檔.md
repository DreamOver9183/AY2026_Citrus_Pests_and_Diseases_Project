1. **`P_TP_LD`（薊馬葉害）從 6 月起就存在於類別清單，但一個框都沒有。**
   它就是現行最弱的 `Thrips_Damage`（AP50 0.489）。這個類別**從一開始就是「有名無實」**，
   到 v5.5 才真正建立標註 —— 這解釋了為什麼它至今仍是全案最不穩定的一類。

3. **12 類實際只有 10 類可訓練**，當時報告中 SSD 混淆矩陣「兩類全 0」的現象已被正確歸因。

## 3. 訓練成果（原始 `results.csv` 重新核算）

### 3.1 六個 YOLO26 run

所有 run 都用 **MuSGD** 優化器、`imgsz=640`、`lr0=0.01`、`epochs=150` ＋ `patience=20`，
在 Kaggle 上執行（args 內路徑為 `/kaggle/input/...`）。

| Run | 用途 | 實跑輪數 | 最佳 mAP50 所在輪 | 最佳 mAP50 | 最後一輪 mAP50 |
| --- | --- | ---: | ---: | ---: | ---: |
| `YOLO26l_Citrus_MuSGD-2` | large | 109 | **ep55** | **0.8823** | 0.8711 |
| `YOLO26n_Citrus_MuSGD` | nano | 124 | **ep55** | **0.8671** | 0.8544 |
| `YOLO26n_P2_Citrus_MuSGD` | nano+P2 | 98 | **ep51** | **0.8657** | 0.8511 |
| `YOLO26n_P2_Citrus_MuSGD_FT-2` | 量化前微調 | 7 | **ep2** | **0.8552** | 0.8463 |
| `YOLO26n_Citrus_MuSGD_Test` | 冒煙測試 | 1 | — | 0.6367 | — |
| `YOLO26n_P2_Citrus_MuSGD_Test` | 冒煙測試 | 1 | — | 0.3223 | — |

兩個 `_Test` run 是 `epochs=1` 的冒煙測試，**不是有效結果**，引用時要排除。

**三個主要 run 都在 ep51–55 見頂後緩降**（large 甚至跑到 ep109 才停）。
這與後來 v9 階段量到的「ep69 見頂、160 輪是純過擬合」是同一個現象，
**收斂點偏早這件事在 6 月的資料裡就看得到了。**

### 3.2 兩個 SSD-MobileNetV3 run

本機訓練（RTX 3050 Laptop 4 GB、Ubuntu、PyTorch 2.12.1+cu130），兩階段策略：
Phase 1（ep1–5）凍結骨幹只練偵測頭，Phase 2（ep6–45）解凍後 6 層全網微調。

| 模型 | 最佳輪次 | mAP@50 | mAP@50-95 | 權重 |
| --- | ---: | ---: | ---: | --- |
| SSD-MobileNetV3-large | ep36 | 0.4717 | 0.3269 | 9.74 MB |
| SSD-MobileNetV3-small | ep40 | 0.4527 | 0.2676 | 6.87 MB |

**SSD 系列在本任務上明顯不可用**（mAP50 僅 YOLO 的一半），主因已查明並記錄：
`320×320` 輸入解析度加上缺乏高解析度淺層特徵融合，
使 `P_SI` 這種極小密集目標的所有預測分數都低於 0.20 閾值，**1,561 個真實框全數漏檢**。

## 4. 三份仍然有用的工程文件

| 文件 | 位置 | 為什麼還有用 |
| --- | --- | --- |
| `Benchmark_process.md` | `Mobile Benchmark.zip` | **現行 ADB 量測流程的原始出處**：`logcat -c` 清日誌 → `am start --es args` → `logcat -d -s tflite`。現行 `tools/run_mobile_benchmark.py` 就是把這套流程工具化 |
| `各項數據計算.md` | `模型成果報告.zip/docs/` | **Detection Jaccard 的來源**。明白寫出「此公式在目標偵測與影像分割領域中也被稱為 Jaccard 指標」，並推導 `Accuracy = TP/(TP+FP+FN)` |
| SSD 兩份 `training_report.md` ＋ `implementation_plan.md` | `模型成果報告.zip/Model/` | 三個具體的除錯結論，見下 |

### SSD 訓練踩到並解掉的三個坑（往後仍可能遇到）

1. **AMP GradScaler 初始縮放溢位**：`GradScaler` 預設 `init_scale=2**16`，
   偵測頭剛隨機初始化時損失偏高，縮放後直接超出 FP16 上限 → 第一步就 `NaN`。
   **改成 `init_scale=2**14` 後正常。**
2. **梯度累積與 LR scheduler 的步數錯配**：原本每個 batch 都呼叫 `lr_scheduler.step()`，
   但權重每 `accumulation_steps` 次才更新一次 → **warmup 比預期快 2 倍耗盡**，
   且會噴 `UserWarning: Detected call of lr_scheduler.step() before optimizer.step()`。
   修法是把 `step()` 移進 `optimizer.step()` 的條件區塊內，並以實際更新次數重算 warmup 步數。
3. **PyTorch 偵測模型的類別 0 是背景**：COCO 標註的 `category_id` 是 `0~11`，
   必須 `+1` 偏置成 `1~12`，模型輸出類別數設 `13`，否則邊界框預測會偏移。

## 5. 盤點時查到的四處數據問題

### 5.1 `best_int8.tflite` 的身分已可確認（更新先前的保留說法）

先前更正報告庫的 benchmark 報告時，我寫「log 只留下檔名與 3.06 MB 大小，
**不足以判定它對應哪一個訓練版本**」。**這批歸檔可以判定了：**

| 證據 | 內容 |
| --- | --- |
| 檔案大小 | `Mobile Benchmark.zip` 內的 `yolo26-nano-p2-w8a32.tflite` = **3,064,091 bytes = 3.06409 MB**，與 log 記載的 `The input model file size (MB): 3.06409` **完全吻合** |
| 原始位置 | `Model/YOLO26-nano-p2-w8a32/runs/detect/YOLO26n_P2_Citrus_MuSGD_FT-2/weights/best_int8.tflite`，同樣 3.06 MB |
| 來源 run | `YOLO26n_P2_Citrus_MuSGD_FT-2` —— 由 nano+P2 的 `best.pt` 以 `lr0=0.001` 微調 7 輪 |

**結論**：那顆模型是 nano+P2 微調版的量化匯出。檔名 `yolo26n_p2_w8a32.tflite` 是
**把資料夾名（`YOLO26-nano-p2-w8a32`）當成檔名**貼上去的，模型本身在匯出目錄裡叫 `best_int8.tflite`。

> **但「w8a32」這個標籤與實測不符。** 本專案 2026-09-07 在同一台手機上量到
> 動態 INT8（真正的 `w8a32`）@640 是 **279.5 ms**，靜態 INT8 是 **147.3 ms**；
> 而這顆模型量到 **145.53 ms**。它的行為是**靜態 INT8**，不是動態 w8a32。
> 引用時**以 `best_int8.tflite` 為準**，不要沿用 `w8a32` 這個名字。

### 5.2 benchmark 報告的兩列錯誤數據**源自原始文件**，不是後來抄錯的

`Mobile Benchmark.zip` 裡 2026-07-14 的原始 `benchmark_report.md`：

- **模型清單寫的是 `best_int8.tflite`（正確）**，改名成 `yolo26n_p2_w8a32.tflite` 是後續進 Notion 才發生的；
- 但表格中 `best_int8` 與 `ssd_mobilenetv3_large_fp16` **兩列的錯誤數值在原始文件裡就已經存在**
  （16.53 ms / 60.50 FPS、50.84 ms 等），而同一份文件 §5 所附的原始 log 是正確的。

**也就是說：錯誤發生在當初填表的階段，原始 log 從頭到尾都對。**
（該錯誤已於 2026-09-07 更正並推送，見報告庫 commit `730e4ef`、`1b947d8`。）

### 5.3 訓練報告把「最後一輪」標成了「最優」

`模型訓練數據報告.md` 對每個模型都寫「最優狀態：Epoch N 達到最優」，但 N 都是**最後一輪**。
以 `results.csv` 重算，**不論用 mAP50 或 ultralytics 自己的 fitness，最佳輪次都不是最後一輪**：

| 模型 | 報告稱「最優」 | 實際最佳 fitness | 實際最佳 mAP50 | 報告引用值 | 實際最佳 mAP50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| YOLO26-large | ep109 | ep89 | **ep55** | 0.8711 | **0.8823** |
| YOLO26-nano | ep124 | ep104 | **ep55** | 0.8544 | **0.8671** |
| YOLO26-nano+P2 | ep98 | ep78 | **ep51** | 0.8511 | **0.8657** |
| w8a32 微調 | ep7 | ep2 | **ep2** | 0.8463 | **0.8552** |

**報告把四個模型都低估了 0.009–0.015 mAP50。**

> 值得注意的是：**引用最後一輪本身是好作法** —— 那正是本專案 v11.5 之後採用的
> `patience=0` ＋ 報 `last.pt` 協定（沒有選擇偏誤）。問題只在於**標籤寫成「最優」**。
> 要沿用這些數字的話，說「最後一輪」而不是「最優」。

### 5.4 「Accuracy」與現行的 Detection Jaccard 公式相同，但**工作點不同、不可直接比較**

6 月報告的 Accuracy 定義 `TP/(TP+FP+FN)` 與現行 Detection Jaccard 完全一致，
但兩者的**算法來源不同**：

| | 2026-06/07 報告 | 現行（v9 之後） |
| --- | --- | --- |
| 算法 | 由 ultralytics 的 P、R **代數換算**：`1/(1/P + 1/R − 1)` | 由**混淆矩陣實際計數** TP/FP/FN |
| 工作點 | P、R 來自 `val()`（conf≈0.001） | 混淆矩陣 conf=0.25 |
| 例 | YOLO26-large：P 0.8983、R 0.8436 → 0.7701 | v12s test：TP 683 / FP 119 / FN 137 → 0.72737 |

**兩邊的數字不可以放進同一張表比較。** 現行 `通用_參考_評估指標與公式.md` 用的是後者。
