## 2. 主線一：即時辨識的採用門檻（v12.2）

### 2.1 門檻長什麼樣，以及為什麼這樣訂

上週會議只說「要有止損標準」。教授的原意更明確：**達不到某個標準，就不要採用即時辨識的功能。**
所以這份標準同時是兩件事——**功能的採用門檻**與**測試的止損點**。
沒過線的後果不是專案失敗，而是 App 少一個功能、改用拍照辨識。

過線要三條同時成立：

| 條件 | 門檻 | 依據 |
| --- | --- | --- |
| 延遲 | 手機 CPU-only 4T，重複輪次**最小值 ≤ 40 ms** | 30 FPS −5 的上緣。`end2end=False` 的圖另加 2 ms 後處理保留 |
| 精度 | test（401 張）**mAP50 ≥ 0.764** | ＝ 現在就能交付的 `fp32@320`（0.78511）− run 間全距 0.021 |
| 逐類 | 任一類 AP50 比 `fp32@320` 低超過 **0.10** 即否決 | 平均值會藏住單一類別崩掉 |

**三條門檻與判準程式的常數都在任何新量測之前登記**（`66747bd`），本輪**無事後修改**。

### 2.2 先算上限，算不到就不跑

用 v12.1 的 12 個實測點對像素數擬合出延遲模型（`fp32` 誤差 0.6%、`int8` 1.5%），
每條路先代入最好情況。這一步**不花任何成本就關掉了三條路**：

| 路線 | 最好情況 | 判定 |
| --- | --- | --- |
| QAT | @320 ＝ 43.5 ms（QAT 產出的是同一種 INT8 圖） | ✗ 連上限都到不了 |
| NCNN / MNN | 要比 `fp32@320` 快 1.62 倍；框架間通常只差數十個百分點 | ✗ 補不上 |
| 拿掉 P2 頭 | @320 約 42.3 ms | ✗ 且無便宜前測 |
| `--xnnpack_force_fp16` | 取決於 CPU 有無 FP16 算術 | ✗ `/proc/cpuinfo` 無 `asimdhp`，不量即關 |

**事後驗證**：第一階段 5 個組合的預測與實測誤差都在 **±4%** 以內，這些關閉的依據成立。

### 2.3 第一階段結果：延遲全過、精度全未過

| 組合 | 有效延遲 | 延遲 | mAP50 | 精度 | 逐類否決 |
| --- | ---: | :-: | ---: | :-: | --- |
| `int8@224` | 28.5 ms | ✓ | 0.62084 | ✗ | 5 類 |
| `int8@256` | 32.0 ms | ✓ | 0.70859 | ✗ | Canker −0.215、Scale_Insect −0.194 |
| `fp32@224` e2e1 | 33.9 ms | ✓ | 0.68938 | ✗ | 3 類 |
| `fp32@224` e2e0 | 34.0 ms | ✓ | 0.69676 | ✗ | 3 類 |
| `int8@288` | 38.0 ms | ✓ | 0.70206 | ✗ | 3 類 |

**根本原因是兩個條件沒有交集**：

| imgsz | 未量化模型 mAP50 | 過 0.764？ | fp32 延遲 |
| ---: | ---: | :-: | --- |
| 320 | 0.777 | ✓ | 66.4 ms ✗ |
| **288** | **0.768** | **✓（+0.004）** | 54.0 ms ✗ |
| 256 | 0.740 | ✗ | 42.6 ms ✗ |
| 224 | 0.675 | ✗ | 32.6 ms ✓ |

`fp32` 最高只到 0.697，**沒有落進第二階段的准入區間 [0.732, 0.764)**，所以第二階段不開，
依計畫 §4.3 觸發 **S2：不採用即時辨識**。距期限 09-22 還有 11 天，提前結案。

### 2.4 唯一上限仍過線的路：QAT@288

延遲 38.0 ms（實測）、精度上限 0.768（未量化模型）、無逐類否決——**三條的上限都過**。
但仍然不做：ultralytics 8.4.121 全庫沒有 QAT 程式碼、紅線 R2 禁止升版；
而且 **0.004 的餘裕只有 run 間全距 0.021 的五分之一**，等於要求 QAT 把 PTQ 掉的 0.066 全部補回來。
這就是「重開即時辨識」的具體內容，不是一句「以後再說」。

### 2.5 兩個量測上的教訓

1. **每組的第一輪都被機身升溫汙染**（最高散佈 120%）。若只量一輪，`int8@224` 會被記成 58.5 ms
   並判為未過——**`--repeat 3` 取最小值的協定在這裡直接改變了結論**。
2. **負截距的擬合式不要外推**：`fp32 ＋ end2end=False` 那條預測 @224 是 25.5 ms，實測 32.05 ms（+26%）。
   改用 `e2e1` 的式子乘 0.975 則只差 0.8%。

## 3. 主線二：B 包從發不出去到回收完成

### 3.1 流程改了什麼

原流程是發給組員從零畫、先交 2 張等我們回覆。掛了兩週。
新流程是 **AI 代理粗標 → 使用者一人逐張審圖細修**：

- 一個人審圖，**框的定義只有一套**（定義不一致正是 `Thrips_Damage` 至今最弱的原因）
- 「先交 2 張」那道同步等待消失了，格式由程式保證
- 做成**資料夾自足的交接包**：`cd` 進去啟動任何 AI 代理即可（`AGENTS.md` ＋ `prelabel.cmd`
  ＋ `tools/prelabel_assist.py`），實際由 Antigravity 執行 021–150

| **EXIF 旋轉** | B 的 150 張有 **118 張**帶旋轉標記 | 已轉正、拿掉標記 |

### 3.3 預標與驗收

Antigravity 第一輪每張只畫 1 個框、漏掉破洞周圍的舊食痕——**成因是規則寫了「褐色破洞不要框」**，
與舊食痕乾裂後的外觀衝突。補上規則 6（有薄膜的破洞算舊食痕）與規則 7（框完再掃整片葉）後重做。

Claude 對 150 張做機械檢查與逐張看圖，處理掉 087／088（壞疽斑塊）與 109–117
（同一片葉的小破洞，**九張一起處理以免同批標準不一致**），並收緊 6 個過鬆的框。
使用者複核同意，並另外判定 047–054 的橫向破裂痕不是舊食痕、029／030 補右側撕裂框。

## 4. 下一步要跑的 ext 臂（預估，尚未執行）

使用者決定**等 A 包結果一起執行**，避免重複建置與訓練。屆時的組成：

| | base | ext 臂 |
| --- | ---: | ---: |
| train 影像 | 7,264 | 7,264（配額中性，不變） |
| train 框 | 18,078 | 約 18,043 |
| 潛葉蛾影像 | 444（111 原始 ＋ 333 增強） | 444（111 原始 ＋ **150 外部** ＋ 183 增強） |
| 潛葉蛾框 | 652 | 約 617 |

**預期結果（估計，不是預測值）**：整體 mAP50 落在 0.79–0.83，與 base 無法區分——
只有潛葉蛾的訓練組成變了，它佔九分之一，就算它動 ±0.08，整體也只動 ±0.009。
**潛葉蛾 AP50 最可能落在 0.64–0.72 的無差異帶**（基準 0.679）；
要算有效需 ≥ 0.72，要算統計上站得住需 ≥ 0.78。

**仍然值得跑**：資料端是模型端全部關掉後唯一沒試過的方向，一輪約 3.1 GPU 小時就能永久關掉
「外部資料有沒有用」這個問題。若明顯變差（< 0.64），那也會證實 P3 記載的域混用警告。

> **執行時的陷阱**：`build_dataset_v5_6.py` 的 `--out` 預設值就是 base 的輸出路徑，
> 而建置前會 `shutil.rmtree(out_root)`。**跑 ext 臂一定要指定不同的 `--out`**，
> 否則會把 base 資料集刪掉重建。
