## 1. 類別 id 的處理（最容易出錯的一步，已從流程中移除）

**組員的標註軟體裡只會有一個類別**，存出來的 `.txt` 首欄一律是 `0`。
真正的 id 由建置腳本重映：

| 包 | 組員看到的類別名 | 存出來的 id | 建置時映射成 |
| --- | --- | ---: | ---: |
| A | `thrips_damage` | 0 | 8（`Thrips_Damage`） |
| B | `leafminer` | 0 | **5**（`Citrus_Leaf_Miner`），由 `EXT_CID = 5` 指定 |

**理由**：要組員在 LabelImg 裡自己建九個類別、還要順序完全正確，
是整條流程裡最容易靜默出錯的一步——順序錯了不會報錯，
只會讓整批標註掛到錯的類別上，而且很難事後發現。
單類別 + 程式重映把這個風險降到零。

`build_dataset_v5_6.py:collect()` 的 `cid` 參數就是為此存在：
呼叫時傳入 `cid=EXT_CID`，忽略檔案裡的原始首欄值。

## 2. A · 薊馬葉害的標註約定

### 2.1 這個包量的是什麼

`Thrips_Damage` 在 v10 的 medIoU 是 0.725–0.727、**R@0.75 只有 0.290–0.375**——
模型找得到病徵，但框畫不準。這通常代表**既有的框本身就不一致**。

20 張的雙人一致性測試回答：**這個類別的邊界能不能被一致定義？**

| 兩人中位 IoU | 結論 | 下一步 |
| --- | --- | --- |
| **≥ 0.85** | 約定可行 | 值得投入全類 208 張重標（v5.7 範圍，不在 v5.6） |
| **< 0.85** | 邊界本質上定不出來 | 依 [v11 §7 中止條件](v11_計畫_資料擴充與切分重新設計.md) **刪除該類別**（[P3 §2.2](v9_說明_P3定位精度改善與測試流程.md) 已分析刪除代價接近零） |

評分：`tools/score_annotation_agreement.py 甲的資料夾 乙的資料夾`。
貪婪最大 IoU 配對，**落單的框以 IoU = 0 計入**——漏標也是不一致，
不能只算兩邊都畫到的部分。輸出除了數字還會印白話結論與後續建議。

### 2.2 書面約定的三條規則

1. 框貼著食痕最外緣，不留白邊也不切邊
2. 一塊連續的食痕 = 一個框
3. **兩塊食痕中間夾的健康葉肉，比兩塊裡較小的那一塊還寬 → 分成兩個框**

> **規則 3 與 [P3 §2.4](v9_說明_P3定位精度改善與測試流程.md) 的差異，是刻意的。**
> P3 建議的是「間隔超過 20px 就分框」。絕對像素值對**程式**是好規格，
> 對**人**不是——標註者的畫面縮放倍率隨時在變，沒有人在標註時去量 20px。
> 改成「和較小那塊食痕比寬度」是尺度不變的，用眼睛比一下就能判斷，
> 不同的人、不同的縮放倍率會得到一樣的答案。這正是這個包要測的東西。

### 2.3 選圖

`prepare_manual_packages.py:prepare_a()`——取自 `Thrips_Damage` 的 **train**
（不碰評估集），依框面積排序後等距取樣 20 張，
確保涵蓋不同受害程度而不是全部同一種難度。
原始檔名記在 `_原始檔名對照.csv`。

## 3. B · 外部潛葉蛾試點

### 3.1 為什麼只有 150 張，以及為什麼一定是獨立實驗臂

網路搜尋與本地 `craft_datasets_undone` 的完整結論見
[v5.6_計畫_無新拍攝的資料強化.md](v5.6_計畫_無新拍攝的資料強化.md) §2.4。摘要：

- **找不到任何附框的柑橘潛葉蛾偵測資料集**，全部要從零標
- 本地五個外部資料集**全部零標註檔**，且都是離體單葉／白底或去背
- 我們的部署域是 2048×1536 田間手持照（有土壤、雜草、自然陰影、入鏡的手指）

**同一個類別裡混入不同域，正是 [P3 §1.4](v9_說明_P3定位精度改善與測試流程.md)
記載的 Thrips 框定義問題的成因。** 所以：

1. 外部影像**只能進 train**，永遠不進評估集（Gate 3 硬性檢查）
2. 必須當**獨立實驗臂**（`--arm ext`），不能悄悄併進 base
3. 規模刻意壓小到 150 張——先用最小的代價回答「有沒有用」，
   而不是先投入 953 張的標註工時再來後悔

### 3.2 選圖

來源：`craft_datasets_undone/.../Large-Scale Lemon Leaf Disease and Pest Image Data/Citrus_Pest`
（542 張、1440×1080、食痕最清楚的一組）。

`prepare_manual_packages.py:prepare_b()` 先用 dHash（閾值 6，與洩漏查驗同一套）
分群去重：**542 張 → 333 個獨立場景**，每群只留一張代表，再隨機抽 150。

> 不去重直接抽 150，可能抽到大量同一場景的重複影像——
> 那等於用 150 張的標註工時換到遠少於 150 個場景。

### 3.3 併入方式：配額中性

外部影像**不增加 train 總張數**，而是佔用 `Citrus_Leaf_Miner` 既有的
`min(4×raw, 1200)` 增強配額：

```
base :  111 raw +   0 外部 + 333 增強 = 444
ext  :  111 raw + 150 外部 + 183 增強 = 444
```

兩臂張數相同、只有合成組成不同，所以 base vs ext 是乾淨的 A/B，
指標差異可以歸因到「外部資料」而不是「訓練集變大」。

## 4. C · 合成影像視覺驗收

### 4.1 為什麼需要人

`--arm cp` 用 `cv2.seamlessClone(MIXED_CLONE)` 把 CLM 食痕融進 train 的
健康株影像。`MIXED_CLONE` 在來源與目標的梯度之間取較強者，
所以會保留食痕紋理、吸收目標葉面的光照——**代價是低對比的食痕可能被洗淡**。

「接縫看不看得出來」「食痕還清不清楚」這兩件事**沒有數值判準**，只能看圖。
所以這是流程裡唯一無法自動化的一道閘。

### 4.2 判準

30 張，每張問三個問題（接縫／食痕清晰度／框準不準），三題全過才算通過。

- **≥ 28/30** → `--arm cp` 放行
- **≤ 27/30** → 不放行，回頭調 `copy_paste_clm.py` 的參數再產一批

說明書裡明寫「不要為了湊到 28 張而放寬標準」——
這道閘的用意就是攔下不好的，少於 28 是有用的結果。

### 4.3 產生方式

`tools/copy_paste_clm.py --qa 30` **獨立跑**，只產 30 張帶編號與標註框的合成圖，
**不建整份資料集**。一份 `OutPut` 約 8.5 GB，為了看 30 張圖而建一份不划算。

## 5. 回收機制

`tools/check_annotation_return.py` 是收件端，兩個用途：

```bash
# 組員先交 2 張時的格式預檢（五分鐘內回覆）
.venv/Scripts/python.exe tools/check_annotation_return.py B --precheck

# 全部回收後的正式驗收；B 加 --install 會併進來源樹（id 0 → 5）
.venv/Scripts/python.exe tools/check_annotation_return.py B --install
```

檢查項目：檔案成對、YOLO 格式（會辨認出誤存成 PascalVOC/JSON）、
類別編號是否全為 0、座標是否在 [0,1] 且框不超出照片。
**錯誤訊息刻意寫成可以直接轉貼給組員的白話**，不需要再翻譯一次。

**「先交 2 張」是流程裡最重要的一道防呆。** 最常見的失誤是輸出格式選錯，
而那要等到打開檔案才看得出來——150 張做完才發現，就是白做一個半小時。
兩份說明書的第 3 步都已改成「先畫 2 張就停下來」，檢查表也有對應的勾選項。
