## 0. 結論先講

- **5 個登記組合的延遲全部過線**（含後處理保留 28.5–38.0 ms）——
  延遲這一關在 224–288 其實做得到，`fp32@224` 是 29.5 FPS。
- **精度全部未過**：mAP50 最高 0.709，門檻 0.764；**每一組都有類別被逐類否決**，
  `Scale_Insect` 與 `Canker` 在五組裡都掉超過 0.10。
- `fp32` 最高只到 0.697，沒有落進第二階段的准入區間 [0.732, 0.764)，**第二階段不開**。
  依計畫 §4.3 觸發 **S2：不採用即時辨識**。距期限（09-22）還有 11 天，提前結案，
  **沒有動用任何 Kaggle 額度**。
- **延遲模型驗證通過**：5 個預測的誤差全部在 ±4% 以內。
  計畫 §3 用它關掉 QAT@320、NCNN/MNN、拿掉 P2 頭，那些判斷的依據成立。
- **唯一上限過線的路是 QAT@288**（§5）——延遲 38.0 ms ✓、精度上限 0.768 ✓、無逐類否決 ✓，
  但精度餘裕只有 **0.004**。它不在本預算內，這是「重開即時辨識」的具體條件。

## 2. 精度：288 以下是懸崖

同一顆 PyTorch 權重、只改推論解析度：

| imgsz | mAP50 | 相對上一格 | `Scale_Insect` AP50 | 過 0.764？ | 逐類否決 |
| ---: | ---: | ---: | ---: | :-: | --- |
| 640 | 0.80897 | — | 0.668 | ✓ | — |
| 320 | 0.77663 | −0.032 | 0.526 | ✓ | 無 |
| **288** | **0.76817** | −0.008 | 0.520 | **✓（+0.004）** | **無** |
| 256 | 0.73969 | −0.028 | 0.413 | ✗ | Scale_Insect −0.136 |
| 224 | 0.67498 | **−0.065** | 0.331 | ✗ | 五類 |

**延遲與精度兩個條件，對 `fp32` 沒有交集**：延遲要 imgsz ≤ 224 才過（§3），
精度卻在 288 以下斷崖式下滑。能同時碰到兩邊的只有 `int8` @ 256–288，
而那一段的 PTQ 代價是 0.031–0.066：

| imgsz | PyTorch | `int8` PTQ | PTQ 代價 |
| ---: | ---: | ---: | ---: |
| 288 | 0.76817 | 0.70206 | −0.066 |
| 256 | 0.73969 | 0.70859 | −0.031 |
| 224 | 0.67498 | 0.62084 | −0.054 |

PTQ 代價對解析度仍然**不單調**，與 v12.1 在 320–640 看到的一致。
**量化傷得最重的是 `Canker`**：PyTorch@288 只比參照低 0.037，`int8@288` 卻低 0.289——
這一類的特徵對 INT8 啟動值特別敏感，不是解析度造成的。

`fp32` tflite 比同解析度的 PyTorch 略高（@224：+0.014 / +0.022），與 v12 在 640、320
看到的方向一致，屬序列化路徑差異，不改變任何判定。

## 3. 延遲：模型的預測成立

| 組合 | 預測 (ms) | 三輪實測 (ms) | 最小值 | 誤差 |
| --- | ---: | --- | ---: | ---: |
| `fp32@224` e2e1 | 32.6 | 45.3 / 33.9 / 34.1 | 33.9 | +4.0% |
| `int8@288` | 36.6 | 50.8 / 37.3 / 36.0 | 36.0 | −1.5% |
| `int8@256` | 30.7 | 30.3 / 30.5 / 30.0 | 30.0 | −2.3% |
| `int8@224` | 25.5 | 58.5 / 26.5 / 27.3 | 26.5 | +4.0% |
| `int8@320` | 43.1 | 43.5（09-07）/ 45.3 / 43.2 / 42.4 | 42.4 | −1.6% |

**計畫 §3 關掉其他路線所依據的延遲模型，在它外推的範圍內誤差不超過 4%。**

兩件要記下的事：

1. **`fp32` ＋ `end2end=False` 的擬合式外推失敗**：它預測 @224 是 25.5 ms，實測 32.05 ms（+26%）。
   計畫已註明這條擬合較差（負截距、最大誤差 4.9%）而改用 `e2e1` 的式子；
   用「`e2e1` 預測 × 0.975」估則是 31.8 ms（+0.8%）。**負截距的擬合式不要拿來外推。**
2. **第一輪全部被熱尖峰汙染**（58.5、45.3、50.8 ms，散佈 34–120%），後兩輪才穩定。
   若只量一輪，`int8@224` 會被記成 58.5 ms 並判為未過——**`--repeat 3` 取最小值的協定在這裡直接改變了結論**。

## 5. 唯一上限過線的路：QAT@288（不在本預算）

QAT 產出的是與靜態 INT8 同一種圖，所以它的**延遲上限就是 `int8@288` 的實測值**，
**精度上限就是同解析度的 fp32**：

| 條件 | 上限 | 門檻 | 餘裕 |
| --- | ---: | ---: | ---: |
| 延遲 | 36.0 + 2 = **38.0 ms**（實測） | ≤ 40 | 2.0 ms |
| mAP50 | **0.76817**（PyTorch@288） | ≥ 0.764 | **0.004** |
| 逐類 | 最差 Canker −0.037 | 跌幅 ≤ 0.10 | 0.063 |

**三條的上限都過了——這是本輪唯一一條。** 但仍然不做，理由有三：

1. **計畫已把 QAT 排除在本預算外**：ultralytics 8.4.121 全庫沒有 QAT 程式碼，紅線 R2 禁止升版，
   只能自寫訓練與轉換流程，工程量以天計。
2. **0.004 的餘裕要求 QAT 補回 PTQ 掉的 0.066 的全部**，其中 `Canker` 要從 −0.289 補回到 −0.037。
   QAT 通常能補回大部分，但「全部」是上限不是期望值。
3. **0.004 只有 run 間全距 0.021 的五分之一**。即使 QAT 做得完美，一次訓練的隨機性
   就足以讓結果落在門檻的任一側。

**這就是計畫 §5「重開即時辨識」的具體內容**：若日後要重開，
方向是「在 288 上做 QAT」，而且要先接受「成功機率不高、餘裕在雜訊以內」這個前提。
