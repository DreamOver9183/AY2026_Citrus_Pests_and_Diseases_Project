## 1. 進度：三條線分開講

| 線 | 現況 | 一句話 |
| --- | --- | --- |
| **資料集** | v5.6，9 類 / train 7,264 / valid 401 / test 401 | **量尺已經修好**：九類的評估誤差 ±2SE 全部 ≤ 0.10，而且沒有新拍任何一張照片 |
| **模型** | v11.5 = 交付基準（test mAP50 **0.810**） | **已經走到底**：模型端連四輪、十一種改動全部無效 |
| **部署** | 本週新開，平台 1 已量完 | **量清楚了**：最好 15.4 FPS，離 30 FPS 差 2 倍 |

**本週最大的變化是第三條線從無到有。** 在這之前專案只量得出精度、量不出延遲，
所以「要不要換更大的模型」這種問題根本無法討論 —— 因為不知道有多少預算可以花。
現在兩邊都量得到，也才有辦法說「v12s 不能上手機」這種話。

---

## 2. 兩個關掉的方向

### 2.1 模型容量 —— 不是瓶頸

**v12s：只改一個變因，模型尺度 n → s，其餘逐字相同。**

```
達標線   test mAP50 ≥ 0.83959      （v11.5 的 0.80959 + 0.03，開跑前寫死在腳本裡）
實得     test mAP50 =  0.81266
Δ                    = +0.00307     → 未通過
```

**3.84 倍參數只換到門檻的十分之一**，而且低於同設定重跑一次的隨機變異（0.021）。
九類裡只有一類的變化超過雜訊地板，**四好四壞一平** —— 若容量真的是瓶頸不會長這樣，
尤其第二弱的潛葉蛾反而變差 0.024。

> **順帶結論：m 尺度不用試了。** s 的 3.84× 都只有雜訊等級，
> m（21 M 參數）沒有理由不同，成本卻會再上去。

### 2.2 部署端調參 —— 30 FPS 達不到

**把官方匯出文件的參數表整份測過**：22 個組合量完整 mAP、18 個量手機延遲、外加 4 種格式。

| 組合 | ms | FPS | mAP50 |
| --- | ---: | ---: | ---: |
| `int8 @ 320`（最快） | 43.5 | 23.0 | 0.719 ← 精度不可用 |
| **`fp32 @ 320`（最佳可用）** | **64.8** | **15.4** | **0.785** |
| `fp32 @ 640`（原始） | 266.3 | 3.8 | 0.816 |

**有效的槓桿只有一個：降解析度**（640→320 加速 4.11×，只掉 0.032 mAP）。
量化、GPU、NNAPI 全部無效或倒退。

> **最反直覺的一條**：相同延遲下 **`fp32@320`(0.785) 勝過 `int8@416`(0.728)**。
> **算力預算該花在降解析度，不是花在量化。**

## 3. 順帶的兩件事（可講可略）

- **官方文件與實際不符四處**，都有程式碼證據。最值得記的是
  `quantize='w8a16'` 文件列為支援、精度也真的無損，但**實測慢 27 倍** ——
  **「文件說支援」不等於「實務上可用」。**
- **與 7 月的手動實機紀錄交叉驗證**：同一台手機、相隔兩個月、不同工具鏈，
  延遲落在 **1.2%** 以內 → 本輪的量測方法可信。
  同時發現該紀錄的彙整表有**兩列數據與它自己附的原始 log 不符**，
  其中一列正好是報告摘要的第一句（會讓人以為 60 FPS 已達成，實際是 6.87 FPS）。
  **已逐欄比對、更正並推送回報告庫。**

## 4. 要在這場會議上決定的兩件事

### 決策 1：30 FPS 是不是真的需要？

- **若互動是「對準葉片 → 拍照 → 出結果」**：65 ms 使用者根本不會察覺，
  **`fp32 @ 320`（15.4 FPS / mAP50 0.785）現在就可以交付。**
- **若必須是即時串流**：這台裝置做不到。要嘛換硬體，要嘛重訓
  （QAT 或直接在 320 解析度上訓練，是僅剩的兩條路）。

> **這是產品決策，不是技術問題 —— 技術面已經量清楚了。**

### 決策 2：人工工作包 A / B 要不要發？

容量既然已被排除，**資料端是目前唯一還沒試過的方向**，而它已經掛了兩週。

| 最弱的類別 | AP50 | 成因 | 對應 |
| --- | ---: | --- | --- |
| `Thrips_Damage` | 0.489 | **框定義不一致**，且**九類裡標註歷史最短**（2026-06 就有代號但零標註，v5.5 才建立） | **工作包 A**：兩人各標 20 張 |
| `Citrus_Leaf_Miner` | 0.652 | 樣本量少（原始只有 111 張） | **工作包 B**：外部 150 張補標 |

**工作包 A 有明確的分歧點**：兩人的中位 IoU ≥ 0.85 才值得全類重標，
否則依既定規則直接刪掉這個類別 —— **這條路怎麼走都會有結論，不會白做。**

> **這週新查到的依據**：翻 `_History/` 的 6 月資料集，`Thrips_Damage`（當時代號 `P_TP_LD`）
> **train / valid / test 全部零標註** —— 類別名從 6 月就在，資料卻是 v5.5 才第一次建立，
> 現在也只有 273 張 / 313 框。**它是九類裡唯一從零開始、最晚建立的類別。**
> 所以問題不只是「標得不一致」，是**這套標註約定本身還沒被驗證過**。

**跨資料集的高低不代表模型強弱**，本專題沒有合法的跨版本基準。

**† 這六列的 Jaccard 是由 P/R 代數換算的，與其他列（混淆矩陣實際計數）不同工作點，不可比。**
**只有最後兩列可以直接相減**（同資料集、同協定，只差模型尺度）。

**如果有人指著 v9 的 0.891 說「不是變差了嗎」，這樣回**：

1. v5r 有 **13.4% 跨 split 近重複影像**，v9 的評估集裡有訓練時看過的照片，**數字灌水**。
2. v9 **只有 8 類，沒有 `Thrips_Damage`** —— 那是九類中最弱的一項（0.489），加進去自然拉低平均。
   v10 取 8 類等效值是 **0.864**，與 v9 的 0.891 只差 0.027，而 v9 那側還有洩漏。
   **實質接近持平，不是退步。**
3. 評估集本身換過（v5.6 為了把誤差壓到 ±2SE ≤ 0.10 而重切）。**量尺變了，刻度不能互換。**

**如果被問的是 6–7 月的 0.871，再加兩條**：

4. 那是 **12 類**資料集 —— 含兩個**健康葉**類別（相對好認、會把平均拉高），
   另有**兩類是零標註**；valid 只有 438 張，`P_SI` 一類就佔框數 68.8%。
5. 那些數字是**最後一輪**卻被標成「最優」。實際峰值更早（large 在 ep55 是 0.882），
   **四個模型都被低估 0.009–0.015** —— 連「當時究竟多少」都要重新界定。

> 補一句：**mAP 高不等於 Jaccard 高。** v9 的 mAP50 全表最高，但 valid 的 Jaccard 只有 0.654 ——
> 因為 `Scale_Insect` 一類就貢獻 563 個背景誤報。兩個指標量的是不同的東西。

## 備答：可能會被問到的

| 問題 | 一句話回答 |
| --- | --- |
| 「不是說更大的模型比較準嗎？」 | 資料量不夠時不會。我們的 raw train 只有 2,353 張，模型早就不是限制。 |
| 「為什麼 +0.003 算沒有進步？」 | 因為同一個設定重跑一次就會差 0.021。這個差距跟擲骰子分不出來，門檻是開跑前就訂好的。 |
| 「換別的推論框架（NCNN/MNN）會不會比較快？」 | 框架之間通常差幾十個百分點，我們缺的是 2 倍。不太可能單靠換框架補上，那一步的價值是排除框架因素。 |
| 「量化不是應該會變快嗎？」 | 動態量化省的是體積不是算力，INT16 甚至慢 27 倍。只有靜態 INT8 真的快 1.81 倍，但掉 0.14 mAP。 |
| 「這台手機是不是太爛了？」 | Snapdragon 662 是 2020 年的入門 SoC，確實舊。但這也是實際會遇到的裝置，結論成立於這台，換機要重測。 |
| 「工作包發下去要多久？」 | 標註本身兩人各 20 張，一次會議的時間。真正的成本是決定要不要全類重標之後的那一輪。 |
| 「v12s 那顆權重還有用嗎？」 | 只當精度上限的參考。它在手機上約 950 ms 一張，不是部署候選。 |
| 「報告庫那兩列數據是怎麼發現的？」 | 拿表格跟它自己附的原始 log 逐欄對。`16.53 ms` 這個數字在整份 log 裡出現 0 次，實際那批跑的是 145.53 ms。已更正推送。 |
